# RLS DENY SURFACE -- one verdict per money / trust / Vera table (HYG-100).
# Enforced by `pnpm check:rls-deny` (scripts/check-rls-deny.mjs), wired into ci.yml.
#
#   <table>  <class>  <denied commands, comma separated, or "-" for none>
#
# CLASSES
#   money    the row IS money, or points at where money lands: a settled amount, a Connect /
#            Stripe identifier, a stored price a seller depends on, a ticket, an internal-currency
#            ledger, or a grant that spends one.
#   trust    standing, roles, permissions, moderation, audit. What the product believes about a
#            person or a Space, which is the other thing nobody may quietly rewrite.
#   vera     Vera's own memory: her config, her autonomy decisions, her dispatches, and the change
#            log that records what she did to a calendar.
#   carrier  matched the census heuristic but is NOT one of the three. A price on a catalogue row,
#            a back-reference to a ticket, a support thread that matched on the word. Every
#            carrier line carries its reason below. A carrier gets no deny matrix here; its wall
#            is somewhere else and the comment says where.
#
# DENIED IS EXACT, BOTH WAYS. For a money / trust / vera line, the commands listed must be exactly
# the commands with NO permissive policy after every migration has been replayed in order. Adding
# a policy to a denied command fails this gate in the pull request that adds it -- that is the
# whole point, and it is what stops `space_vera_changes` from quietly gaining the update policy
# that would turn an append-only record into an editable one. REMOVING the last policy from an
# allowed command fails too: a money table nobody can read any more is a feature going dark, not a
# table going safe (check:rls's `lastPolicyDropped` arm says the same thing about a different
# question).
#
# WHAT "DENIED" MEANS AT RUNTIME, since the two arms do not look alike:
#   insert  -> SQLSTATE 42501, "new row violates row-level security policy". A raised error.
#   update  -> zero rows. The USING clause of a command with no policy admits nothing, so the
#   delete     statement succeeds having touched nothing. NO ERROR IS RAISED, which is exactly why
#              this is worth a test: an app that does not check the row count cannot tell the
#              difference between "denied" and "already done".
#   select  -> zero rows, same reason.
#
# 47 classed (32 money, 11 trust, 4 vera) + 15 carrier = 62, seeded 2026-09-23 from
# lib/database.types.ts and the migration replay. The classed count is floored in the gate.
