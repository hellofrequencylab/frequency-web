# Frequency Experience (the mobile app)

The Frequency app for phones, in `mobile/`. Android first. Decided in [ADR-1865](DECISIONS.md). What is
built and what is left is tracked in [`BUILD-BACKLOG.json`](BUILD-BACKLOG.json) (`LIVE-1121`,
`DEF-MOBILE`), never here.

**This pass is the CyberUnicorn 5000 remote only** (owner scope, 2026-10-19: "Right now, I just want a
phone app to control it"). It needs no Frequency account and no network. The member experience is
designed to slot in later (§6). Install and run: [`mobile/README.md`](../mobile/README.md).

permission in this pass.

## 2. Design: the Frequency system only

The app wears the **live Frequency theme**, the one the website renders under
`<html data-design="frequency">`. Values come from `app/themes/frequency.css` (the alias layer) over
`app/themes/frequency/core.css` (the export), plus the members kit (`kit-members.css`,
`members-ui.css`). Where the alias layer overrides the export (the cool canvas `#F4F6F7`, the teal
accent, the blue-to-aqua pastel, the AA-fixed muted text, the status hues), the alias layer wins,
because that is what a member sees. Faces, the icon sprite and the logos come from
`design_handoff/frequency/`. Rules kept: the pastel only for the one primary action, progress and live
dots; Unbounded at weight 500 only; sentence case and no em dashes in copy; no hex outside `tokens.ts`.

When the web theme changes, change the values in `tokens.ts`. The kit reads roles, so no component
changes.

## 4. The CyberUnicorn link

The device protocol is `cyberpunkunicorn-os/apps/remote/PROTOCOL.md` (v1). The phone half:

- **Framing:** `rpc {json}\n` out. `@rpc` replies and `@evt` events in. Every other line is Bruce's log
  and is ignored. A full-width `＠` prefix is accepted too. `mobile/src/device/protocol.ts` (tested).
- **Concurrency:** one request at a time per transport, each with a timeout of 5 s (8 s for
  `cli.run`/`hat.probe`, 12 s for the `frequency.*` tag commands). `mobile/src/device/client.ts`.
- **USB:** the CH340 at 115200 8N1. **DTR and RTS are set false once and never touched again**, because
  they drive the ESP32's EN and IO0 and asserting them resets the board. The Kotlin module exposes no
  way to set them. Bytes cross the bridge as base64; UTF-8 is decoded in JS with a streaming decoder.
- **Bluetooth LE:** react-native-ble-plx against Bruce's serial service
  `4371ec0b-3d43-49f9-b731-7c72a4a7bb91` / characteristic `d555ed97-bf2a-4f46-b3eb-d1fcdd7325e9`,
  advertised as `CU5K`. MTU 517 requested on connect, one write with response per line, and
  notifications joined and split on `\n`.
- **Tag writer:** the owner pastes the Space's check-in link (Settings, Check in, Copy). The app checks
  its `/n/<uuid>?s=` shape, warns on a host other than frequencylocal.com, and sends
  `frequency.write_tag {url}` only: one NDEF URI record and nothing else (`docs/LOYALTY.md` §6). It never
  builds or retypes the link. `frequency.read_tag` reads it back and the app compares the URL.
- **Internet relay:** a "coming soon" choice in Connect (`mobile/src/device/relay.ts`). The design is
  PROTOCOL.md §6.

## 5. Sharing `lib/contract`

The repo is not a workspace and stays that way. The app compiles against `lib/contract/index.ts` as the
web does, without copying it: `mobile/tsconfig.json` maps `@frequency/contract` to the file and `zod` to
the app's own copy, and `mobile/metro.config.js` watches only `lib/contract/` and resolves its `zod` from
`mobile/node_modules`, so a build that never installed the web still bundles. The app pins the web's zod
version. The root `tsconfig.json`, `eslint.config.mjs` and `vitest.config.ts` exclude `mobile/`. Today
only the Frequency tab reads from it (`CONTRACT_VERSION`), which keeps the path proven by every bundle.

## 6. Planned site integration (not built)

The app is laid out so these land without a rewrite. A first version of the member half was written and
then taken out by the scope change. It is in this branch's history at commit `73dc345f4`: sign-in, the
session in SecureStore, `/api/v1/session/bootstrap`, push, the Rewards and check-in screens, and the two
endpoints `GET /api/v1/rewards` and `GET /api/v1/spaces/checkin-links`.

1. **Member experience, in the Frequency tab.** Sign in with supabase-js (email code, or a magic link to
   `frequency://auth/callback`), the session in Expo SecureStore, every read through `/api/v1`
   (APP-CONTRACT): Regulars stamp cards and codes, Zaps and streak, check-in by tapping a venue tag with
   the phone's NFC (`POST /api/v1/nodes/{id}/capture`), and native push (`/api/v1/push/devices`).
2. **The device API, `/api/v1/devices/*`** (branch `live/nfc-device-checkin`): the tag writer can then
   offer the owner's Spaces' signed links instead of a paste, and a member card can be issued and
   scanned.
3. **The internet relay** (PROTOCOL.md §6): `POST /api/v1/devices/realtime-token`, Realtime RLS on
   private `device:<id>` channels, device ownership and `GET /api/v1/me/devices`. The relay transport
   reuses `RpcClient` and the line parser unchanged.
