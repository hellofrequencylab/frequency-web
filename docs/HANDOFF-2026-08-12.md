# Handoff — the build that stopped reaching production (2026-08-12)

> ## ✅ ANSWERED — read this box, then the doc as history (2026-08-12)
>
> **No commit crossed the disk. The build had been ~1.5x over budget for months and #2098's five
> extra functions were what finally did not fit.** Full record: **ADR-1002** in
> [`DECISIONS.md`](DECISIONS.md).
>
> The measurement this doc kept asking for: Vercel's report counts the UNIQUE file set, but the
> disk cost is the PER-FUNCTION sum, because the builder copies each function's traced set into its
> own directory. Summing the `.nft.json` files gives **16.73 GB across 480 functions**.
>

> build** — for an image codec that 18 routes use. `app/opengraph-image.tsx` was the ROOT metadata
> image, Next inherits metadata images into every page's metadata module, that module imports
> `next/og`, and `next/og` loads `sharp` internally. One file at the root of `app/` put a 17.7MB
> shared object into every page in the app.
>
> The card was a pure function of build-time constants and rendered identical bytes every time, so
> it is a static file now. **16.73 GB → 9.80 GB**, verified locally, guarded by `pnpm check:og-trace`.
>
> ⚠️ **The bisect below is superseded — do not run it.** #2098 adds no dependency (its
> `package.json` diff is two `check:*` scripts) and no `next.config.ts` change. Re-landing it is now
> an ordinary re-land, not an experiment. What is NOT superseded: §"Threads parked while this fire
> burned" is still live, and 9.80 GB is still mostly duplication — see the tail of ADR-1002 for the
> next two lines.

**Start here.** The Studio/Vera wizard work (#2098) is merged, reviewed and correct as far as CI
can tell, and it **cannot reach production**. Every deploy carrying it compiles clean and then
dies with `ENOSPC` about nineteen minutes into `Deploying outputs`. The last tree that reached
production is `3f8d62b`. The site has been serving it the whole time and members saw nothing.

The cause is somewhere in the code that merged on the night of 2026-08-11. That is **confirmed by
experiment**, not inferred. What has NOT been established is *which part*. Finding that is
tomorrow's first job, and it is one build long.

## The evidence

Two builds, same project, same region (`cle1`), same container class, an hour apart.

| | Green control (`3f8d62b` tree) | Every build carrying #2098 |
| --- | --- | --- |
| Compile | 2m | 3m |
| `Deploying outputs` → `Deployment completed` | **28 seconds** | **~19 minutes, then `ENOSPC`** |
| Build cache upload | 1.05 GB in 17s | never reached |
| Outcome | ✅ Ready in 3m 1s | 🔴 Error |

The green control's log, in full, because the 28 seconds is the number that matters:

```
05:33:44  Deploying outputs...
05:34:12  Deployment completed
05:34:37  Uploading build cache [1.05 GB]
05:34:54  Build cache uploaded: 17.030s
```

Note that it uploaded a **1.05 GB build cache without difficulty**. Any theory that blames the
cache has to explain that line.

That green control is the whole argument. It ran **after** all the failures, on the same
infrastructure, with the build cache disabled, and it deployed normally. Platform, region,
container size and account state are therefore all excluded.

The failing report's only measured deltas:

```
Output files:   873 MB
Node modules:  1073 MB   (948 MB on the last healthy build)
Dynamic functions: 408   (403 on the last healthy build)
```

⚠️ Do not over-read the node_modules delta. Part of it is self-inflicted: with the build cache
forced off, pnpm re-materialises `.pnpm-store` on disk, and the 106 MB `@supabase/cli-linux-x64`
binary then appears **twice**. That is why `VERCEL_FORCE_NO_BUILD_CACHE` was removed again.

```bash
git checkout main && git pull
git revert --no-commit -m 1 <the-revert-commit-that-landed-2102>
```

In plain terms: put #2098's tree back on top of the reverted main, push it as a branch, and watch

### Bisecting inside #2098

It touches 216 files, so bisect by **what could plausibly cost disk**, not alphabetically. In
rough order of suspicion:

1. **Function count.** 403 → 408. Find the five new dynamic routes (`git diff --stat` on
   `app/**/page.tsx` and `route.ts`) and check whether any pulls a heavy module into the server
   bundle. 408 lambdas that each grow a little is 408 × the growth.
2. **`outputFileTracingIncludes`** in `next.config.ts`. Anything added here is copied into *every*
   matching function's bundle. This is the single highest-leverage place for output to balloon
   invisibly.
3. **A heavy import reaching a shared server module.** `lib/studio/registry.ts` imports all 14
   manifests; if any manifest transitively pulls something large (a parser, a WASM blob, an SDK)
   into a module the shared layout also imports, it lands in every function.
4. **`serverExternalPackages`.** If a package that used to be external stopped being external, its
   native binary gets traced into the bundle instead of loaded from `node_modules`.

The measurement that settles each hypothesis is the same: build locally, then
`du -sh .next/standalone` and `du -sh .next/server` against the same command on `3f8d62b`.

## Unblocking the revert (#2102)

Blocked on exactly one thing: a CodeQL alert on `app/(main)/events/event-spark.tsx:274`,
`DOM text reinterpreted as HTML`, high severity.

**It is a false positive, and this repo already documents it.** The line is
`<img src={thumbSrc} />` where `thumbSrc = safeUploadPreviewSrc(thumbUrl)` and `thumbUrl` comes
from `URL.createObjectURL`. `lib/safe-image-src.ts` exists in the reverted tree, byte-identical to
main's, and its own comment block explains that CodeQL does not model these helpers as sanitizers,
that `createObjectURL` embeds nothing attacker-controlled, and that inline suppression comments are
not honoured by GitHub code scanning. The only supported route is dismissal.

**Action:** dismiss the alert as *False positive* in the Security tab. Auto-merge is armed and the
PR lands itself.

## What I got wrong, so nobody re-runs it

Recorded because two of these look like the obvious answer and both are dead ends.

1. **"It's the Turbopack build cache."** Next 16.3.0 did flip
   `turbopackFileSystemCacheForBuild` to default-on, and the cache did reach 1.4 GB. Two PRs went
   in on that theory ([#2100](https://github.com/hellofrequencylab/frequency-web/pull/2100),
   [#2101](https://github.com/hellofrequencylab/frequency-web/pull/2101)). Their ADR left the ledger
   with them in the revert, so the number it had is deliberately not cited here — `pnpm check:adr`
   is right to fail a citation a reader cannot follow.
   **A build with the cache disabled entirely at the platform level failed identically.** The PRs
   are defensible on their own merits — a 1.4 GB cache is worth not carrying — but they did not
   fix this and they are not the cause.
2. **"It's the unpaid Vercel invoice."** The account does show a failed payment. It is not the
   cause: the `development` project on the *same account* was deploying in 18–33 seconds
   throughout.
3. **Killing builds to "free concurrency".** At least one cancelled production build might have
   completed. Cancelling mid-flight destroys the evidence you are trying to collect. **Let builds
   finish and read the log**, unless the queue is genuinely blocking a fix that is ready to go.

The general lesson, for whoever picks this up: the control experiment (deploy the last known-good
tree on the current infrastructure) took three minutes and settled in one shot what two hours of
theorising did not. **Run the control first.**
