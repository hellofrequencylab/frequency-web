## ADR-1655: Every member can be found on /network: the directory filters in the query and pages with a range (LIVE-661)

**Status:** Accepted · 2026-09-29 · backlog `LIVE-661` (closed here, filed by the DEF-DOMAIN split, ADR-1624) · numbered 1655 by the orchestrator's assignment · re-tested first per [ADR-1082](DECISIONS.md) · no migration

**Context.** `app/(main)/network/page.tsx` read the first 500 active profiles by name (`.limit(DIRECTORY_FETCH_LIMIT)`) through the service-role client, then ran every filter over that slice in the page: region, Circle, City, Online now, Topic, Role and the name search. It rendered the first 48 and told the member to narrow with search. Past the 500th name, narrowing could not help, because the search only ever looked inside the slice. A member there could not be found by browsing, by any facet, or by typing their own name. Re-tested on main at `8b0b1909e`: the cap and the client-side filters were both there, and the row's probe failed. `/circles/page.tsx` carries no cap on main, so this ADR is `/network` only.

**Decision.**

1. **The filters run in the query.** `lib/connections/directory-page.ts` `scopeDirectoryQuery` applies the listing gate (`is_active`, `directory_visible`, not `ghost_mode`, the demo gate) and then each URL filter: region (resolved from the name to `nexus_region_id`), Circle and City (resolved to the active members' profile ids), Online now (a `last_seen_at` cutoff at `ONLINE_MS`), Topic (a quoted `entity_types` containment), Role (`member` also matches a null rung, as the card has always shown it), and the name search (`sanitizeOrTerm`, one `or()` of `ilike` over `display_name` and `handle`, the same shape `/search?tab=people` uses). It is framework-free, so the probe and the suite run the real rules.
2. **The cards page with a range.** One page is 48 cards, the old render slice, ordered by `display_name` then `id` so page edges are stable. `?page=` rides in the URL next to the filters, so a shared link lands on the same page. The pager is Links only (Prev, Next, Page X of Y, a match count), so the page stays a Server Component with no client JS.
3. **Nearby first survives paging.** The `members_near` lead (at most 60, already privacy-gated by the RPC) goes first on page 1, read through the same scope, and is excluded from the alphabetical read. `directoryWindow` places each page across the join, so no member shows twice and none is skipped.
4. **The cards stream.** The listing is its own async component behind a Suspense boundary keyed on the query and page, with a card skeleton. The header, filters and rail paint first. The facets and the Most popular place stream behind their own boundaries.
5. **Failures are not "no matches".** A page past the end (a filter narrowed the set under a shared `?page=`) clamps to the last page. Any other failed read throws to the route's error boundary.
6. **The side reads are scoped too.** Members Worldwide and Total members are an exact head count. Online now is its own scoped read of 8. The facet options and the Most popular place read a bounded sample of 1000 (PostgREST `max_rows`), because PostgREST has no DISTINCT or GROUP BY. The sample only chooses which options to offer. It never decides who is listed or found.
7. **Privacy is enforced twice.** The SQL scope drops opted-out and ghosting members, and every returned row still passes `isListableInDirectory` ([ADR-1203](DECISIONS.md)) before it renders or is counted.

**Rejected.** Raising the cap (moves the cliff, and PostgREST stops at 1000 anyway). A search RPC with a migration (the PostgREST filters express every facet the page has, and a migration would have held the fold). Keyset pagination (range is enough at this size, and `?page=` is the shareable shape the other directories already use). Resetting `page` inside the shared facet and search controls (they serve other pages; the clamp covers a stale page).

**Consequences.** Anyone listable in the community can be found by name or facet and reached by paging, however large it grows. Nearby members still lead. The facet option lists and the Most popular place can miss a value held only outside the 1000-row sample once the community passes that size; the members themselves stay findable. Circle and City filters send the member ids in the URL, which stays short while circles are capped. No help page changes: members already search and filter the same way.

**Rows.** `LIVE-661` closed here. Tests: `lib/connections/directory-page.test.ts` (a 900-member in-memory community finds member 842 by name; opted-out and ghosting members never list; 1234 members with a nearby lead are each reached exactly once across pages), `lib/connections/directory-visibility.test.ts` (pin moved from the single capped read to the scoped reads).
