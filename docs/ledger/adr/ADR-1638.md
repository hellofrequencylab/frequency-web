## ADR-1638: A phone that loses signal gets Frequency's own offline page instead of the browser's error, and the service worker still never stores a page or an API response (LIVE-702)

**Status:** Accepted · 2026-09-29 · backlog `LIVE-702` (filed by [ADR-1624](DECISIONS.md), the owner replan that made the mobile site an active lane) · re-tested first per [ADR-1082](DECISIONS.md) · numbered 1638 by the orchestrator's assignment · no migration, no dependency

**Context.** Re-tested on `main` at `fb91c7b48`: `public/manifest.json` declares `display: standalone`, so a member can install the site, and `public/sw.js` (registered at scope `/` by `components/push/registration.tsx` on every `(main)` mount) handled push and notification clicks only, with a header reading "No offline caching yet". A page load with no signal therefore showed the browser's error page, which in an installed app looks like Frequency is broken. The premise held. The same header named the reason nothing was cached: every page here can carry one member's data.

**Decision.**

1. **Pages are network first and never stored.** A same-origin GET navigation goes to the network and the response is handed back untouched. Only when `fetch` rejects (no connection) does the worker answer, with `/offline.html` from its own cache. No page response is written to any cache, so the worker can never serve stale member data, or another member's data on a shared phone or after a sign-out. Being offline is the better failure.
2. **One precached page, standalone.** `public/offline.html` is a static file with inline styles (the DAWN light and dark values copied from `app/globals.css`, since a cached file cannot read the app's custom properties), the app icon, and no build asset. It is precached with `/icons/icon-192.png` at install. Copy per CONTENT-VOICE: "You're offline", one plain sentence, one deadpan line, a "Try again" button, and a reload when the `online` event fires. No em dashes. The row's idea of promising the practice timer was dropped: the timer is a page, and pages are not stored.
3. **Only public, content-addressed static files are stored.** `/_next/static/` (hashed, immutable) is served from the cache first; `/icons/` and `/images/` (public but unhashed) go to the network first and fall back to the stored copy. A response is stored only when it is a same-origin (`basic`) 200 without `no-store` or `private`. The static cache is capped at 150 entries, oldest out first.
4. **Everything else is left alone.** Non-GET, cross-origin, `/api/`, RSC fetches, `/_next/image` (it can proxy a signed private file), `/_next/data` and range requests get no `respondWith`, so the browser fetches exactly as if no worker were there.
5. **Versioned caches.** Names are `frequency-offline-<v>` and `frequency-static-<v>` from one `OFFLINE_VERSION`; activate deletes any `frequency-` cache that is not current and leaves other prefixes alone. Changing `offline.html` means bumping the version, which the page's own header comment says.
6. **Push is untouched.** The offline half is its own `install`, `activate` and `fetch` listeners at the bottom of `public/sw.js`; the push, notification-click, and original install/activate handlers are byte-for-byte what they were. A failed precache is caught so it cannot fail the install and take push down with it; the navigation handler then answers with a short inline page in the same voice (status 503).
7. **The decision is pure and tested where the browser runs it.** `offlineStrategy`, `isCacheableResponse` and `isStaleCache` are top-level functions in the worker. `test/contract/offline-worker.test.ts` evaluates `public/sw.js` in its own `vm` global with fake `caches` and `fetch`, checks those functions directly, and drives install, activate and fetch end to end. Mutation-checked: storing a navigation, routing `/api/` into a cache, dropping the precache, skipping cleanup, storing a `private` response, and letting a failed precache reject the install each fail a test.

**Deploy safety.** No package added. Nothing new in `app/`, `components/` or `lib/`, so nothing new is reachable from `components/layout/app-shell.tsx`, a root layout or a server function. Registration is unchanged, so this works wherever the push worker already registers (an installed app, and any browser with `PushManager` and the VAPID key set); widening registration belongs to the push rows (`LIVE-701`, `LIVE-703`), whose files this change does not touch.

**Rejected.** Caching pages for offline reading (the header's standing rule, and the brief's: stale or cross-member data is worse than offline). An `app/offline` route (its HTML would depend on hashed chunks that a later deploy removes, and it would run the root layout). A service-worker library such as Workbox (a dependency for three strategies). `importScripts` of a separate helper file (a second fetch and a second update path, for a few short functions).

**Consequences.** An installed Frequency opened with no signal shows a branded page that reloads itself when the signal returns, and build files a member already loaded keep working. The row's probe loads the real worker in a `vm` sandbox and fails on `main` at the first arm (no offline page, no fetch handler).

**Rows.** `LIVE-702` (closed by this change at fold time).
