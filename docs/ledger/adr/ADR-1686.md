## ADR-1686: The Journey editor's save actions ask canEditJourney, the gate the editor page already asks, so a Space manager who can open the editor can save in it (LIVE-732)

**Status:** Accepted · 2026-09-30 · backlog `LIVE-732` (filed and closed here) · re-tested first per [ADR-1082](DECISIONS.md) · no migration

**Context.** The LIVE-689 builder (#3099) found that the Journey editor at `app/(main)/journeys/[slug]/edit` and the Server Actions it calls disagree about who may edit. The page admits through `canEditJourney` (`lib/journeys/authoring.ts`): the author, a platform operator (`admin.access`), or a manager of the Space the Journey belongs to (`canEditProfile`: owner, admin or editor), for a Journey that is not in the root space. The actions in `app/(main)/journeys/[slug]/edit/actions.ts` ran their own `authorPlan` copy, which admitted only the author or an operator, and `setLeafAnchorAction` carried a third inline copy of that. Re-tested on `main` at `451c500f0`: the premise held, so a Space editor opened the editor and every add, update, move, remove, compose, Vera change, anchor, warm-up and export came back refused.

Which rule is right is settled in the code. `lib/journeys/authoring.ts` names itself "the one authoring gate shared by the editor route and every editor server action, so they can never drift", and describes team authoring: a Space's editors may edit the Space's Journeys, not only the teammate who created it. Every other editor surface already asks it: the settings, visibility, cover, meeting and delete actions (`assertOwner` in `app/(main)/journeys/actions.ts`), the Journey guide, the launch context, and the event-to-Journey link. The edit actions were the one surface left on the older author-or-operator rule.

**Decision.**

1. **Widen the actions to the page's rule; do not narrow the page.** `authorPlan` returns the plan only when `canEditJourney(plan.id, caller.id)` admits the caller. `setLeafAnchorAction` (keyed by plan id) asks `canEditJourney` as well. The file no longer reads `admin.access` or compares `author_id`, so there is one predicate and it lives in `lib/journeys/authoring.ts`.
2. **The name `authorPlan` stays** so the in-flight LIVE-689 change to the same file merges cleanly. Its doc comment says it is the shared gate and not to re-derive the rule. The refusal copy is unchanged.
3. **One test asks both sides the same question.** `app/(main)/journeys/[slug]/edit/gate.test.ts` runs the real `canEditJourney` with only its readers stubbed, and checks the page and the actions together: a Space manager opens and saves, the author and an operator still do, a non-managing Space member and a signed-out caller are refused by both with nothing written, and a root-space (personal) Journey admits no Space managers. The existing `actions.test.ts` stubs the gate open, since what it locks is reorder and bulk-op behavior.

**Rejected.** Narrowing the page to author-or-operator (it would contradict the team-authoring rule every other editor surface enforces, and strand Space editors who can already edit a Journey's settings). A second exported predicate beside `canEditJourney` (a second rule is what drifted).

**Consequences.** A Space owner, admin or editor can build a Space's Journey end to end. Who is refused is unchanged for everyone else. The row's probe reads the page, the actions and the gate, and fails if any exported edit action skips the shared gate or the file re-derives the rule.
