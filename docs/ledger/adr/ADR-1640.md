## ADR-1640: A content report is refused unless its target row exists (LIVE-652)

**Status:** Accepted · 2026-09-29 · backlog `LIVE-652` (closed here) · completes the SEC-4 wall in `reportContent` · no migration

**Context.** `reportContent` already refused a target type outside `VALID_TARGETS` and an empty id. It then inserted through the admin client. The reports table stores `target_id` as a UUID with no foreign key (the target is polymorphic), so Postgres would accept any well-formed id. A signed-in member could file a report for a post, comment, dispatch, member, event or Guestbook note that did not exist, and the moderation queue would show a target nobody could open. SEC-3 (the action on the report must name the same target the report names) was already in the file.

Re-tested on this tree before the change: between `Missing report target` and `from('reports').insert` the action read only `reports` (the duplicate-pending check). No other table. The backlog probe failed for that reason.

**Decision.**

1. **`reportContent` reads the target before it writes.** After the empty-id guard, `reportTargetExists` does one keyed read per type. A missing row returns `fail('Invalid report target')`, the same line as a bad type, so the two holes are not distinguishable.
2. **The table is the one the moderator already acts on.** Post and comment are `posts` (a comment is a row with `parent_id` set; a top-level post is `parent_id` null). Dispatch is `dispatches`. Member is `profiles`. Event is `events`. Guestbook is `spotlight_guestbook`.
3. **A non-UUID id is missing.** `target_id` is a UUID column; a string that would error in Postgres is refused the same way, without a write.
4. **The action is the wall.** The admin client bypasses RLS, so the existence check cannot live in a policy. Duplicate-pending still runs after the target is known to exist.

**Rejected.** Returning a distinct "that is gone" line (enumerates existence). Trusting the dialog's id (the dialog is not the wall). Adding a polymorphic FK (the target spans six tables; this row is the read, not a schema change).

**Consequences.** A signed-in member cannot park a phantom report in the queue. Reporting a real post, comment, dispatch, member, event or Guestbook note is unchanged. Help does not change: members already report something they can see.

**Rows.** `LIVE-652` closed here. Tests: `app/(main)/feed/report-actions.test.ts` (source-shape of the missing read, one case per type).
