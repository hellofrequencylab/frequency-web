## ADR-1635: A PR records its row and its ADR as fragment files under docs/ledger, never as edits to the two shared ledger files, so ledger changes stop conflicting and PRs merge in parallel (HYG-145)

**Status:** Accepted · 2026-09-29 · backlog `HYG-145` (filed and closed here, as the first row fragment) · extends [ADR-1043](DECISIONS.md) (the one list) and [ADR-1446](DECISIONS.md) (AGENTS.md is an index) · supersedes the "every PR folds" half of HYG-032's fold for new work · keeps [ADR-1509](DECISIONS.md)'s cross-PR id gate, widened to fragments

**Owner, 2026-09-29 (~19:50Z):** "Change the rule or something. I don't want stuff like this jamming me up."

**Context.** Every PR edited `docs/BUILD-BACKLOG.json` (to close its row and prune it from a `meta.slate` wave) and `docs/DECISIONS.md` (to append its ADR). So every merge conflicted every other open PR on exactly those two files, and on nothing else. Merges ran strictly one at a time, each preceded by `git merge origin/main && pnpm fold`, and on 2026-09-29 about twenty finished PRs sat in that line. The fold tool made each resolution mechanical; it could not make them parallel, because the conflict is structural: two PRs appending to one file always meet.

**Decision.**

1. **Fragments.** A PR writes its ledger change as files, one per row and one per ADR, and does not touch the two shared files:
   - `docs/ledger/rows/<ID>.json`. A new row is its full row object, plus an optional top-level `"wave": "W7"` that places it on that wave. An edit to an existing row is `{ "id", "patch": {...}, "append": {...}, "wave": "W7" | null }`: `patch` sets keys (null deletes one; objects such as `verify` are replaced whole), `append` concatenates onto a string field (the usual `detail` closing paragraph) or an array, and `wave` moves the row or, with null, takes it off every wave.
   - `docs/ledger/adr/ADR-<n>.md`. The full ADR in this file's format; its first line is the heading, and it declares one ADR. Its relative links are written from `docs/` (check:docs-links resolves them from there), because the text lands in this file when it is compacted.
2. **One loader.** `scripts/lib/ledger.mjs` is the only reader of the two files. `loadBacklog()` returns the base JSON with every row fragment applied, deterministically: base entries in file order with their edits, then new rows in id order. `loadDecisions()` returns the base text plus each fragment ADR in number order. A broken fragment (misnamed, an edit to a missing row, a full row whose id exists, an unknown wave, an ADR number already declared) is a structural failure that names the file. check:backlog (both probe arms, stale-open and regressed-done, now judge the merged view), check:adr, check:id-collisions, check:shipped-ids, `pnpm backlog` and `pnpm packets` all read through it. check:one-list adds one rule: `docs/ledger` holds fragments and nothing else. With no fragments the view is the base file, so nothing assumes a fragment exists.
3. **Waves stop needing edits on close.** The loader drops every done or parked id from every `meta.slate` wave at read time, whichever file closed it. `validateSlateWaves` keeps its one-wave-per-token arm (HYG-134) and loses the parked/done arm, which the loader now makes impossible. HYG-047's probe reads the merged view.
4. **Collisions.** Two PRs editing the SAME row write the same fragment path and conflict in git, which is correct: that is a genuine disagreement. Two PRs editing different rows never meet. check:id-collisions reads the ids a PR introduces from its fragment file names (no download) as well as from the two base files, and counts the base tip's fragments as the base.
5. **Probes that parse the JSON.** The parent probes that read child status (PROG-D5, PROG-D6, DEF-HARDEN) and HYG-047's slate probe now `require("./scripts/lib/ledger.mjs").loadBacklog()`, so a child closed by a fragment counts. A new probe that reads a row or an ADR uses the loader, never the raw file. LIVE-034's rule stands: no test-runner names in a probe.
6. **Old PRs: convert, then parallel (owner ruling 2026-09-29).** A branch that already edits the two files runs `pnpm ledger:from-diff`. It diffs the branch's copies against its merge base with `origin/main`, writes each changed row and each new ADR as a fragment, proves the fragments reproduce the branch's rows on top of main, and restores both files to main's copy. It refuses, writing nothing, when an edit cannot be a fragment (a row both sides changed, an ADR edited in place, a deleted row, a `meta` edit outside the wave placements, an id main has since taken); such a PR stays on the legacy path, `git merge origin/main && pnpm fold`, which still works. The steps at fold time:
   ```
   git fetch origin main
   pnpm ledger:from-diff        # add --drop-preamble if it names a theme-index edit you can discard
   git add docs/ledger docs/BUILD-BACKLOG.json docs/DECISIONS.md
   git commit -m "Move this PR's ledger edits to fragments (ADR-1635)"
   git merge origin/main        # the two shared files no longer conflict
   pnpm check:adr && pnpm check:backlog && pnpm check:one-list && pnpm check:id-collisions
   ```
7. **Parallel merges.** The owner's ruleset on `main` (17640795) already has "Require branches to be up to date before merging" unchecked; the required checks are checks, analyze, lint, test, Vercel and db-tests, and force pushes are blocked. Nothing changes there: a fragment PR merges as soon as its own required checks pass, beside every other one. Because no PR is re-tested against the tip before it merges, the CI run on every push to `main` (the same guards, including check:adr and check:backlog over the merged view) and the production build's postbuild gates are the backstop for two PRs that are each green alone and clash together.
8. **Compaction (owner ruling 2026-09-29: "When 30+ pile up").** Fragments are folded into the two base files by a housekeeping PR when more than 30 are waiting; there is no cron. check:backlog and `pnpm backlog` print a notice past that count. The folding tool itself, `pnpm ledger:compact` (byte-stable, idempotent, the merged view identical before and after), and the builder helpers (`pnpm ledger:close`, `ledger:add`, `ledger:adr`) are a follow-up row; until then a builder writes the fragment by hand, which is one small JSON file.

**Rejected.** A merge queue or strict up-to-date merging: it serialises the same conflict instead of removing it. Splitting DECISIONS.md or the backlog into many files at once: a migration of 1,400 ADRs and 1,000 rows that every open PR would conflict with, for no gain over fragments that compact into the same files. A custom git merge driver: it runs locally only, and GitHub's merge would still report the conflict.

**Consequences.** A feature PR's ledger change is two new files that no other PR touches, so ledger edits no longer serialise merges. The base files change only in a compaction PR, a legacy PR, or a deliberate edit to `meta`. Every reader pays one directory read per load. A probe or a script that parses `docs/BUILD-BACKLOG.json` directly still works for any row no fragment touches, and misreads one that a fragment edits; the parent probes above are converted, and the rest (PROG-D7, PROG-R10, LIVE-034, HYG-108, LIVE-176, HYG-023, LIVE-447, LIVE-478, HYG-124) are listed for the follow-up.

**Rows.** `HYG-145` (filed and closed here, as `docs/ledger/rows/HYG-145.json`). Probes re-pointed at the merged view: `PROG-D5`, `PROG-D6`, `DEF-HARDEN`, `HYG-047`.
