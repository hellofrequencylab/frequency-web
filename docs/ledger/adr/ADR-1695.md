## ADR-1695: A migration already merged to the base branch counts as carried for an in-flight PR (HYG-159)

**Status:** Accepted · 2026-09-30 · backlog `HYG-159` (filed and closed here) · amends ADR-1690 (HYG-158) · owner ruling of 2026-09-30 ("soften it") · no migration

**Context.** ADR-1690 lets a PR that touches no migration pass `check:migrations` when production has a ledger row the tree lacks, provided another open PR carries the exact file. On 2026-09-30 #3108's merge ref was built at 03:50Z, LIVE-666's #3107 (carrying `20270345011400_circle_channels`) merged at 03:53Z, and #3108's run at 03:54Z found no open carrier and failed, although the file was already on main. The same race recurs for every migration in the queue: any PR whose run starts before the migration PR merges and reads the ledger after.

**Decision.** `findInFlightCarriers` first lists `supabase/migrations/` at `origin/<base>`, which the workflow fetches before the guards run. A ledger row whose exact `<version>_<name>.sql` is there counts as carried, and the report says `already on <base>; update this branch`. No API call is made for it. Rows not found on the base tip go to the open-PR lookup as before. If the base tip was not fetched, the lookup falls through to the open PRs, never to a pass.

**Rejected.** Waiting for the owner or an agent to update every branch after each migration merge (the jam the ruling names). Forgiving any ledger row newer than the tree (the 2026-08-12 out-of-tree SQL would pass).

**Consequences.** A PR that raced a migration merge stays green with a warning that tells it to update its branch. Main, migration PRs and every other drift shape are unchanged.
