## ADR-1690: A migration in flight warns on a PR that touches no migration, and still fails a migration PR and main (HYG-158)

**Status:** Accepted · 2026-09-30 · backlog `HYG-158` (filed and closed here) · owner ruling · amends the ledger rule of `check:migrations` (a ledger row with no repo file is drift) · builds on ADR-1670 (HYG-154) and ADR-1668 (HYG-150) · no migration

**Context.** A migration is applied to production in its own window, right around its own PR: push the PR, apply the SQL together with its `supabase_migrations.schema_migrations` row at the repo version and name, then merge. Between the apply and the merge, main has no file for that ledger row. On 2026-09-30 at 03:02Z `check:migrations` on #3097, which touches no migration, read `20270345009800 commerce_order_transfers` (LIVE-622, file on open PR #3100) as "Production ran SQL that is not in the tree" and failed the required `checks` job. Every open PR does the same for every migration in the queue. The owner ruled: soften it so it stops blocking unrelated PRs.

**Decision.**

1. **One status, four conditions.** `in-flight`, exit 0, only when ALL hold: the run is a pull request whose diff names no file under `supabase/migrations` (`prTouchesMigrations` is `false`, never unknown); the only disagreement is ledger rows with no repo file (no unapplied file, no name mismatch); every such row's version is newer than every migration in the tree; and every such row's exact `<version>_<name>.sql` is at the head of another open pull request against the same base.
2. **Loud, never a pass.** The full drift report still prints, followed by the in-flight files and the PR carrying each. In Actions a `::warning` annotation shows on the PR's checks page.
3. **Read cheaply.** The open PRs are read with HYG-150's seam: one pulls listing, every head fetched in one `git fetch --depth=1 --filter=blob:none`, file names from `git ls-tree`. It runs only when the drift already has the in-flight shape, so a parity run spends nothing.
4. **Every doubt is strict.** A push to main, a PR that touches a migration, a lookup that fails or has no token, a row older than the tree, a row no open PR carries (including one whose PR closed unmerged), and every other drift shape fail exactly as before.

**Rejected.** Applying migrations after merge instead of before (the migration PR itself would then read "authored but never applied" and the deploy would ship code ahead of its schema). Forgiving any ledger-only row newer than the tree without the open-PR check (SQL applied from outside the repo, the 2026-08-12 incident, would pass every PR). Updating every open branch by hand after each merge (the jam the ruling names).

**Consequences.** Unrelated PRs stay green while a migration is in flight, with a visible warning. Main still fails if a migration is applied and its PR never merges, and so does every PR once that PR is closed. The lookup costs one extra REST call, only on runs that already drift.
