## ADR-1685: A circle, event, hub, nexus or practice rail loads its modules in one request instead of one per module (LIVE-655)

**Status:** Accepted · 2026-09-30 · backlog `LIVE-655` (closed here) · re-tested first per [ADR-1082](DECISIONS.md) · generalises [ADR-550](DECISIONS.md) (the Space rail's one-bundle provider) · closes the "Speed" half of `docs/ADMIN-RAIL.md` §6.4 · no migration

**Context.** Re-tested on `main` at `451c500f0`: `components/admin/modules/space-rail-data.tsx` was still the only rail bundle provider, and every inline module on a circle, event, hub, nexus or practice rail called its own `'use server'` getter from a mount effect. Two facts make that slow, both read from the code rather than assumed:

1. **Next.js sends Server Actions one at a time per client.** `node_modules/next/dist/docs/01-app/02-guides/server-actions.md`: "If a user triggers three actions in quick succession, the second waits for the first to finish ... do not rely on `Promise.all` to parallelize Server Actions from the client. If you need parallel work, do it inside a single Server Action." So a rail's reads queued, and the rail filled in at the sum of their round trips. Each request also pays `proxy.ts`'s own `auth.getUser()` (a network call to Supabase Auth) before the action runs.
2. **Three of those reads were often the same read.** On a circle, Settings, Guided and the Circle Quest block each called `getCircleAdminData` (a circle row, the capability resolve, then seven parallel reads). On an event, Settings, Guided and the Danger zone each called `getEventAdminData`. Hub and nexus Settings and Danger shared one read, and so did practice Guided and Settings.

**Decision.**

1. **One read table.** `lib/admin/entity-rail-reads.ts` names, per kind, the reads each rail module makes on mount (`circle.engage` → `engage`, `practice`, `journeyRun`, the three bodies that one box stacks; `extra:engage` → the Circle Quest block's `admin`; `extra:danger` → the event Danger zone's `admin`). Pure data, no imports.
2. **One request.** `components/admin/modules/entity-rail-actions.ts` exports one Server Action, `getEntityRailBundle(kind, key, reads)`. It runs each named read once, in parallel (`Promise.allSettled`), inside that one request, by calling the SAME getter the module calls with the SAME key. It adds no read and no authority: every getter still re-checks its own capability and returns null for a viewer who lacks it. Unknown kinds and reads are ignored, so the client cannot name a getter the table does not hold. A read that throws comes back `{ ok: false }` and is logged, so the fallback that follows is visible.
3. **One provider, mounted with the sections.** `components/admin/modules/entity-rail-data.tsx` (`EntityRailDataProvider`) wraps the rail body's section list in `admin-bar-body.tsx` and asks for the reads of the nodes actually mounted there, so the server never does more work than the self-fetching modules did. The request fires from the provider's own effect as soon as the mounted list has something to read, while the `next/dynamic` module chunks are still downloading; a list that settles a render late still gets the one request. It wraps the browse branch only, so a search (which unmounts every module) unmounts it too, and clearing the search fetches fresh, as before.
4. **A drop-in for the getter.** Each module's mount effect now calls `useEntityRailRead(kind, read, getter)(key)` where it called `getter(key)`. The hook serves the bundle's slice when the provider holds it for this kind, key and read, and otherwise calls `getter(key)`: outside the provider, on another entity, a read the provider did not ask for, a failed read, or a failed bundle (which the browser console names, so the fallback is never silent). Reloads after a write keep calling the getter directly, so they are never served the mount snapshot. 25 module files, 26 call sites. `hub.layout` and `nexus.layout` are untouched: both are `render: 'link'` since ADR-846 and never mount.

**The reading, before and after** (a manager opening the full rail; what the client sends, then what the server runs):

| Rail | Requests before | Requests after | Getter runs before | Getter runs after |
|---|---|---|---|---|
| Circle | 10, one after another | 1 | 10 (`getCircleAdminData` 3 times) | 8 |
| Event | 5 | 1 | 5 (`getEventAdminData` 3 times) | 3 |
| Hub | 4 | 1 | 4 (`getHubAdminData` twice) | 3 |
| Nexus | 4 | 1 | 4 (`getNexusAdminData` twice) | 3 |
| Practice | 3 | 1 | 3 (`getPracticeAdminData` twice) | 2 |

The hub row is measured, not reasoned: `components/admin/modules/entity-rail-data.test.tsx` mounts the four real hub modules with their getters counted, and reads 4 getter requests and 0 bundles without the provider, then 1 bundle carrying `admin`, `people`, `insights` and 0 getter requests inside it, with the same guide, form value and archive control on screen. The other rows are counted from the read table and the module files, not measured against a live database (the container holds no credentials). `proxy.ts`'s `auth.getUser()` falls with the request count (a circle rail: 10 to 1), and the rail's wall time goes from the sum of its reads to the slowest one. Reads that depend on the entity id stay their own requests and are unchanged: Guided's `loadStudioSteerAction`, the Danger zone's two plan reads, the Layout tuner's reads, and every write.

**Not done here, on purpose.** Each getter run still resolves the viewer and the capability rows for itself. `React.cache()` does not dedupe inside a Server Action: react-server-dom's `getCacheForType` returns a fresh `Map` when no Flight render is active, and Next's action handler (`executeActionAndPrepareForRender`) calls the action outside one. So `getCachedUser` and `currentViewer` memoise within a page render, not within an action, and eight getter runs in one bundle resolve the viewer eight times, as the eight separate requests did. A shared resolve (the ADR-550 `buildXData` shape) per entity, or an action-scoped memo under `lib/auth.ts`, is the next saving; both touch the gates, so neither rides along with a P3.

**Rejected.** Fetching every read of a kind whenever its rail opens (more server work than before for a viewer whose rail carries fewer modules). A client-side promise cache per getter (still one sequential request per distinct read). Letting the modules batch themselves after mount (each `next/dynamic` chunk lands in its own tick, so one batch window splits into several requests). Per-entity copies of the Space provider (five providers to keep in step, where one table and one hook serve all five).

**Consequences.** A circle, event, hub, nexus or practice rail sends one request on open. A module outside the rail, or any miss, behaves exactly as before. Every module now paints when the slowest read in the bundle lands: the one module at the head of the old queue could paint sooner than that, and every module behind it waited longer. If one read ever dominates, the ADR-550 answer applies (split it into its own phase), not a return to per-module requests. A new rail module that is not in the table self-fetches, which is correct and costs only the saving; the row's probe fails if a wired module goes back to fetching for itself, if a call site passes a different getter than the bundle runs for that read, or if the bundle runs a read no module consumes.

**Rows.** `LIVE-655` (closed here).
