## ADR-1663: Every commercial email footer prints the one platform postal line (LIVE-728)

**Status:** Accepted · 2026-09-29 · backlog `LIVE-728` (filed and closed here) · no migration

**Context.** CAN-SPAM asks every commercial email to carry a valid physical postal address. The LIVE-707 builder, drafting the Space email acceptable-use policy (PR #3066), found that a plain Space campaign and a Space drip step went out with a footer that ended at the Unsubscribe link. The block-built shell (`lib/email-studio/shell.ts`) already printed "Frequency Labs Holdings, 802 Caminito Azul, Carlsbad, CA 92011", but from a private constant nothing else could reach.

Re-tested on main at `60567b67e` before building (ADR-1082). The same bare footer sat in seven plain renderers, not two: `renderCampaignHtml` in `lib/spaces/campaigns.ts` (also the event broadcast), its twin in `lib/spaces/campaigns-send-due.ts`, `renderStepHtml` in `lib/spaces/drip-runner.ts`, `renderEmail` in `lib/nurture/runner.ts`, `campaignEmail` in `lib/studio/campaigns.ts`, `actorEmailHtml` in `lib/automations.ts`, and the Studio agent note in `lib/studio/agent.ts`.

**Decision.**

1. **One source.** `lib/email-studio/postal.ts` owns the line: `PLATFORM_POSTAL_LINE`, and `postalFooterHtml()` for the plain renderers. It is pure and imports nothing, so a cron runner can pull it without the nav registry `lib/site.ts` carries.
2. **The block shell reads it.** Its private `POSTAL_ADDRESS` is gone. A per-Space `EmailBrand.address` still overrides the shell line, unchanged.
3. **All seven plain renderers append it** under the Unsubscribe line. The platform campaign text part prints it too. The Space plain renderers have no brand input, so they print the platform line, the same default the Space block editor already sends.
4. **`lib/email.ts` falls back to the same line.** Its footers (the `emailShell` footer every transactional and member email renders, and the scan-intro, signup-recovery and event-claim text parts) read `COMPANY_POSTAL_ADDRESS`. That var was never set, and unset fell back to the site host with no address. They now read `envString('COMPANY_POSTAL_ADDRESS', PLATFORM_POSTAL_LINE)`: a set value still wins, and unset or blank prints the platform line. `docs/LAUNCH.md` and `docs/NETWORK-CRM.md` now call the var an optional override.
5. **The address is not new.** It is the value the shell already sent in production. Nothing was invented.

**Rejected.** Making `COMPANY_POSTAL_ADDRESS` the only source: it was never set, so every footer would still print no address until an owner step, and a missing var would fail silently. Merging the three byte-identical Space renderers into one: a refactor this row does not need.

**Consequences.** Every commercial footer Frequency renders, block or plain, carries the postal address. Changing the address is a one-line edit in `postal.ts`, and `postal.test.ts` fails if it loses its street, state or ZIP. The env var stays as an override for an owner who wants a different address, such as a PO box.

**Rows.** `LIVE-728` filed and closed here. Tests: `lib/email-studio/postal.test.ts`, `lib/email.test.ts` (unset, blank and set), plus a postal case in `lib/spaces/campaigns.test.ts`, `lib/spaces/campaigns-send-due.test.ts`, `lib/spaces/drip-runner.test.ts` and `lib/studio/campaigns.test.ts`.
