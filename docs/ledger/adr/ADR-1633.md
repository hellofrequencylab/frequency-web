## ADR-1633: The marketplace discovery stamp is written only when it is missing, when the view changes it, or when it is an hour stale, so a repeat view and a Server Action send no Set-Cookie (LIVE-711)

**Status:** Accepted · 2026-09-29 · backlog `LIVE-711` (closed here) · owner ruling 2026-09-29 ~19:10Z, "Fix it": write the cookie only when it is missing or its value would change, attribution unchanged · amends when [ADR-1419](DECISIONS.md) §1 writes the stamp, not what it records · re-tested first per [ADR-1082](DECISIONS.md) · numbered 1633 by the orchestrator's assignment · no migration

**Context.** Re-tested on `main` at `3be7bedd4`. `proxy.ts` calls `stampMarketplaceView` on every request to `/market/<id>`, `/journeys/<slug>` and `/discover/journeys/<slug>`, and `mergeStamp` always sets `iat` to now, so the signed `fq_mkt` value is new on every request and the proxy sends a Set-Cookie with each one: page loads, router fetches, prefetches and Server Actions alike. On a Server Action that is not free. Next merges a cookie the proxy sets into the action's cookie store and reports the action as "cookies changed", and the client answers by dropping its whole prefetch cache and re-prefetching every visible Link. LIVE-649 traced the member-route request flood to the same shape with the `fq_acct` and `fq_ask` marker cookies and left this stamp alone because it is the take-rate contract. The premise held: the row's probe fails on `main` on the repeat view.

What the stamp means today, read from the code and kept exactly: it holds up to 20 product ids and 10 Journey slugs, newest first, and a view moves its id to the front (the caps evict the oldest). One `iat` covers the whole stamp, `verifyStamp` rejects it seven days after that `iat`, and the cookie's max-age is the same seven days, so any discovery view slides the window for everything in it. It is last-touch for the window and accumulating for the set; a storefront visit neither stamps nor clears it.

**Decision.**

1. **`stampMarketplaceView` returns null when nothing would change.** It still verifies the held cookie and merges the view. If the held stamp is valid, the merged product list and Journey list equal the held ones in value and order, and the held `iat` is under `MARKETPLACE_ENTRY_REFRESH_MS` (one hour) old, it returns null and the proxy writes nothing. Order is compared because it is the eviction order: re-viewing an older product still moves it to the front and writes, so a skipped write never changes what the 20-product cap keeps.
2. **The window still slides, at most an hour behind.** A repeat view an hour or more after the last write re-signs with a fresh `iat`. The stamp therefore lapses between seven days less an hour and seven days after the last discovery view, where before it lapsed exactly seven days after. That hour is the whole difference, and it can only end a stamp earlier, never later, so no sale that classifies `self` today classifies `network` after this. `MARKETPLACE_ENTRY_MAX_AGE`, the caps, `verifyStamp`, `entryPointFromStamp` and checkout are unchanged.
3. **A missing, expired or forged cookie is written fresh**, as before.
4. **The rule lives in the stamp module, not in LIVE-649's marker helper** (`lib/nav/marker-cookie.ts`, [ADR-1617](DECISIONS.md)). That helper refreshes on a full page load because a marker carries no clock of its own. The stamp carries `iat`, so an age test keeps the window on every request type, including the router fetches that a page-load rule would never refresh. The shared idea, write only when the browser does not already hold the value, is the same, and the stamp does not import the helper.

**Rejected.** Re-signing only past half the max age (the row's suggestion): the window could end three and a half days after the last view, a real change to ADR-1419. Re-signing on every full page load (LIVE-649's rule): a buyer who only ever reaches the product by in-app navigation would never slide the window. Lengthening the max age by an hour to make up the slack: it would move the contract's constant for an hour of granularity.

**Consequences.** A repeat Market or Journey view, and any Server Action on that page, sends no `fq_mkt` Set-Cookie for an hour after the last write, so the stamp no longer drops the client's router cache on those actions. A new product or Journey, or a re-view that reorders the list, still writes at once. Tests: `lib/commerce/marketplace-entry.test.ts` (the pure rule) and `proxy-consent.test.ts` (the real proxy, a repeat GET and a Server Action POST send no `fq_mkt`). Each fails against the code before this change.
