## ADR-1618: A practice's main Pillar is its domain_id, never the first key of its Focus map, so a save that edits one Focus can no longer move it (LIVE-650)

**Status:** Accepted · 2026-09-29 · backlog `LIVE-650` (closed here; filed by HYG-135) · completes [ADR-1604](DECISIONS.md) §5 (which fixed the Studio builder only) · the Focus map is [ADR-992](DECISIONS.md), the split [ADR-438](DECISIONS.md) and the ledger that reads it [ADR-1131](DECISIONS.md) · re-tested first per [ADR-1082](DECISIONS.md) · numbered 1618 by the orchestrator's assignment for this wave

**Context.** Re-tested on `main` at d332f1335 on 2026-09-29, from the repo (no database read). `practices.focus_details` is `jsonb`, and jsonb keeps no key order: Postgres stores object keys by length and then bytewise, so a map read back from the row lists its Pillars in id order. `cleanFocusDetails` still returned `primary: keys[0]`, and `updatePractice` still set `domain_id` to it on every write that carried a Focus map. The builder's map is built in memory with the primary first (ADR-1604), so its saves were right; any caller that sent a map read back from the row (`updatePracticeAction` takes any `PracticeEdit`, the Studio kernel writes whole paths) reset `domain_id` to the Pillar whose id sorts first, and with a split whose secondary sorted first, cleared the split. How many stored rows hold a `domain_id` that is not their first stored key is not measured (no database read).

**Decision.**

1. **The primary is `domain_id`.** It is one of the `focus_details` keys and never "the first" of them. The type docs, the Practice manifest, the create action and the builder say so.
2. **One pure rule keeps it on write**, `keepPrimary` (`lib/practices/split.ts`, rule 5 of that file). The declared primary is the patch's `domain_id` when the patch names one, else the row's current `domain_id`; while it is still one of the Focuses it stays, whatever order the keys arrive in. Only a primary that left the set (or a row that has none, as at create) is replaced, by the first Pillar id of the map as handed. That fallback is the caller's order, not jsonb's: at create it is the order the author chose, and in the builder it is the Focus the editor then shows as primary.
3. **`cleanFocusDetails` picks no primary.** It trims and bounds the map and nothing else.
4. **One read of the row's Pillar columns.** The Focus clause needs the stored primary and the split clause needs all four columns, so `updatePractice` reads them once for both.
5. **A named primary in the same patch now wins** while it is one of the Focuses. Before this, a patch carrying both `domain_id` and `focus_details` silently took the first key instead.

**Rejected.** Sorting the fallback (the builder shows its map's first key as primary, and a sorted fallback would make the saved primary disagree with the one on screen). Storing the Focuses as an ordered array (a migration and a reshape of every reader for a fact `domain_id` already holds). Removing the builder's primary-first seed (it keeps the editor's display and the stored primary one, and ADR-1604's probe pins it). A backfill of rows whose primary already moved (not measurable from the repo; a moved primary is still a valid Focus, and the author can set it back now that a save keeps it).

**Consequences.** Editing one Focus's instructions, adding a Focus, or saving a map read back from the row keeps the main Pillar and the Zap split. Removing the primary Focus still moves the primary, as it must. `lib/practices-primary-pillar.test.ts` drives the real `updatePractice` with every Focus map in every key order and fails against the old rule; `split.test.ts` owns `keepPrimary`. No migration.

**Rows.** `LIVE-650` closed here.
