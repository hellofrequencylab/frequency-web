## ADR-1630: Installing Frequency is offered by one card after a member's RSVP or post (never on a first visit) and always in Settings, with the browser's prompt fired by a tap on Android and the Share steps on iPhone; that card also carries the push ask, so the two never stack (LIVE-703)

**Status:** Accepted · 2026-09-29 · backlog `LIVE-703` (closed here) · WM, the mobile-site lane of [ADR-1624](DECISIONS.md) (native iOS stays parked in `DEF-MOBILE`) · owner ruling 2026-09-29 ~19:15Z, "After first RSVP" · stacked on `LIVE-701` ([ADR-1629](DECISIONS.md)) and reusing its browser read · re-tested first per [ADR-1082](DECISIONS.md) · no migration

**Context.** Re-tested at `682e88b46` (LIVE-701's branch over `main` at `3be160428`), from the repo only. Nothing under `app/`, `components/` or `lib/` handled `beforeinstallprompt`, so on Android the only install offer was Chrome's own mini-bar, which it shows on whatever visit the page first qualifies, including the first. `public/manifest.json` (a static file; `app/layout.tsx` points `metadata.manifest` at it, and nothing generates it) shipped `"screenshots": []`, so Chrome's richer install sheet had nothing to show. On iPhone and iPad there is no install prompt at all: Safari installs only through Share, Add to Home Screen, and no page told anyone that. That matters beyond installing, because web push on iPhone works only from the Home Screen (LIVE-701), so an iPhone member in a Safari tab could not get notifications and was told only in one line on Settings. The owner ruled: show an install card after a member's first RSVP or first post, plus a permanent "Install the app" option in Settings; never on a first visit; Android fires `beforeinstallprompt` from a tap; iPhone shows the Share steps; the manifest gains a narrow and a wide screenshot.

**Decision.**

1. **Capture before hydration, in the root `<head>`.** `lib/pwa/install-capture.ts` (a leaf with no imports) exports `INSTALL_CAPTURE_SCRIPT`, which `app/layout.tsx` inlines beside the theme bootstrap. It calls `preventDefault()` on `beforeinstallprompt` and parks the event on `window` for a later tap, clears it on `appinstalled`, and announces both with a `frequency:installprompt` event. A component listener could miss the event (Chromium fires it once per load, often before the shell hydrates, and not again until the next full load), and `preventDefault()` is also what keeps Chrome's own mini-bar off, which is itself a first-visit install offer. The same script stamps `frequency.firstSeen` in `localStorage` on the device's first load and flags that browser session, so "first visit" is the session that first loaded Frequency, capped at 12 hours. Local only, never sent; blocked storage reads as a first visit, which only hides the offer.
2. **Pure decisions, reused detection.** `components/push/install.ts` holds `installAvailability` (installed, prompt, ios-steps, none), `isFirstVisit`, and `nudgeOffer`, all pure, over LIVE-701's `readPushEnv` (the same iOS and Home Screen read decides whether push works and whether installing can happen). `promptInstallFromTap` calls `prompt()` before its first await, so it stays inside the tap, and releases the captured event before showing it (a prompt shows once).
3. **ONE card, not two.** `DeviceNudge` (`components/push/device-nudge.tsx`) replaces LIVE-701's `PushNudge` under a Going RSVP and in a Circle a member belongs to, and now also renders after a post in every `Composer` (lazily, through `next/dynamic`, because the composer is reachable from the `(main)` shell). `nudgeOffer` decides what it carries: **install** only in the RSVP and post contexts, never on a first visit, once per device (`frequency.installNudge`), and only where it can happen; **push** when a tap can ask, once per device (`frequency.pushNudge`, unchanged). When both apply (Android, returning, notifications not yet asked) they share the one card, each with its own button. The first eligible card on a load claims the only slot, so a Circle card and a post card never stack even though their flags differ.
4. **iPhone: the install step is the push step.** In a Safari tab push reads `ios-install`, which is not askable, so the card there is the install card: the three Share steps with no button, plus "That is also where notifications work on iPhone." It obeys the install rules: not on a first visit, not in a Circle. This changes LIVE-701 on purpose, whose card showed the Home Screen line on a first visit and in a Circle: that line is an install ask, and the owner's ruling now governs every install ask.
5. **Settings keeps the way in.** A new "Install the app" section on `/settings` (chip and anchor `#install`, after Notifications) renders `InstallSettingsCard`: the button when the browser handed over its prompt (including one that arrives after render), the Share steps on iPhone, "You are using the installed app" from the Home Screen, and a browser-menu line elsewhere. Member how-to: `content/help/getting-started/install-the-app.md`, linked from Your settings.
6. **Two real screenshots.** `public/manifest.json` lists `/screenshots/home-narrow.jpg` (390x844, `form_factor: narrow`) and `/screenshots/home-wide.jpg` (1264x800, `wide`). Both are crops of the repo's own visual baselines of the public home page (`test/e2e/__screenshots__/visual.spec.ts/home--dawn-light-{mobile,desktop}.png`, captured 2026-09-28 by the visual suite), re-encoded as JPEG. Real product pixels, not placeholders. The signed-in captures (feed, nearby) were not usable: the suite masks member data in magenta. `*.jpg` is already outside the proxy matcher, so the files serve without a session.

**Rejected.** Listening from a component (misses an early prompt). Leaving Chrome's mini-bar on (a first-visit offer the ruling forbids). Two cards, one per ask (they stack after an RSVP on Android, and on iPhone they say the same thing twice). Offering install in a Circle (not in the ruling). Treating the whole card as first-visit gated (it would delay LIVE-701's Android push ask, which the ruling did not touch). A server-side "account age" test for first visit (it needs a profile read threaded into every RSVP and composer caller, and a device-level visit is what the ruling describes). Generated or mocked screenshots (the baselines are real). Anything native (`DEF-MOBILE`, parked).

**Consequences.** ✅ An Android member who comes back and RSVPs Going or posts sees one card with "Install the app", and the browser's install sheet opens only from that tap, now with two screenshots. ✅ An iPhone member in Safari sees the Share steps and learns that is where notifications work, instead of nothing. ✅ Settings always has the option. ✅ Nothing offers installing on a first visit, and the two one-time asks never stack. ⚠️ Every existing device reads its first load after this ships as a "first visit", because the stamp is new, so the install card waits one more session for everyone. ⚠️ The iPhone steps say "Share" for every iOS browser; Chrome and Firefox on iOS put Share in a different place. ⚠️ The screenshots show the public home page, not a signed-in screen; replacing them with unmasked in-app captures needs a seeded demo account and is not a row. ⚠️ Visual baselines for `app-settings` change (one new section); pr-compare is advisory.

**Rows.** `LIVE-703` (closed here). `LIVE-701` (its `PushNudge` becomes `DeviceNudge`; its rules are unchanged except point 4). `DEF-MOBILE` (parked, untouched).
