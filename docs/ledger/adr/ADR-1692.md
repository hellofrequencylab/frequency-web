## ADR-1692: A direct message holds two people, enforced by the database, and a scope leader reads the other stewards of the scope they lead (HYG-139)

**Status:** Accepted · 2026-09-30 · backlog `HYG-139` (closed here) · re-tested first per [ADR-1082](DECISIONS.md) · finishes the follow-ups promised by migrations `20260604220000` ([ADR-088](DECISIONS.md), DMs become one-to-one) and `20260614100000` ([ADR-218](DECISIONS.md), scoped stewardship) · helper placement per [ADR-847](DECISIONS.md) · migration `20270345011600`, authored here and applied by the orchestrator

**Context.** Two migration comments promised a follow-up that never shipped. `20260604220000_group_dms_to_private_rooms.sql` moved every group conversation to a private room and said "A FOLLOW-UP migration adds the hard 1:1 invariant on conversations once this backfill is verified in prod." `20260614100000_stewardships.sql` said "Scope-leader read of co-stewards is a follow-up (avoids a recursive policy)." Re-tested on `main` at `7cba7d186`: `conversation_participants` has no trigger at all, so "two participants" is only a habit of the three app writers (startConversation, findOrCreateDirectConversation, the moderation warning), and `stewardships` still has the one read policy (own edges and platform staff). Production, read by the orchestrator on 2026-09-30 at 03:27Z: 6 conversations, every one with `migrated_to_room_id` and `name` null and exactly 2 distinct participants, 6 distinct pairs, 0 self-pairs; `conversation_room_migration` no longer exists. So the rule holds for every row today.

**Decision.**

1. **A trigger, not a constraint.** A CHECK cannot count sibling rows, so `public.enforce_conversation_one_to_one()` runs BEFORE INSERT OR UPDATE OF `conversation_id, profile_id` on `conversation_participants`. It refuses a third participant (SQLSTATE 23514, `conversation_is_one_to_one`) and any new participant on a conversation that moved to a room (23514, `conversation_migrated_to_room`), whose members belong in `room_members`. The same person twice was already refused by the primary key `(conversation_id, profile_id)`; the pgTAP file pins it rather than adding a second rule.
2. **It locks before it counts.** The trigger takes `FOR NO KEY UPDATE` on the parent conversation, which serializes participant changes per conversation without conflicting with the `FOR KEY SHARE` the foreign key check takes. Two sessions each adding a second person cannot both see one and land three. Each count reads a fresh READ COMMITTED snapshot after the lock is granted.
3. **What it leaves alone.** A read marker (`last_read_at`) never fires it. A participant re-pointed inside their own conversation (a profile merge) is not counted twice. Leaving is a delete and is untouched, so a thread may drop to one. The function is SECURITY DEFINER so the count is never filtered by the writer's RLS, EXECUTE is revoked from `public`, `anon` and `authenticated` by name (ADR-959), and `scripts/function-grants.txt` declares it `internal`.
4. **Who a scope leader is comes from the code, not from this ADR.** An ACTIVE stewardship edge on exactly that `(scope_type, scope_id)`, whatever its role, which is `leadsScope()` in `lib/core/stewardship.ts` and `stewardsScope()` in `lib/messages/room-scope.ts`; or the place's leader column (`circles.host_id`, `hubs.guide_id`, `nexuses.mentor_id`), which the resolver in `lib/core/load-capabilities.ts` ORs with the edge and `room-scope.ts` checks through `leadsPlace()`. An outpost has no leader column. A suspended edge is not leadership. A leader reads every edge on the scope they lead, the suspended ones included, and nothing on any other scope: a hub guide does not read the circles under the hub through this policy.
5. **The helper breaks the cycle.** A stewardships policy that queries stewardships is the 42P17 recursion. `private.leads_scope(text, uuid)` is SECURITY DEFINER, lives in `private` (off the REST surface, ADR-847), returns a boolean about the caller only, and is executable by `authenticated` because a policy runs as the querying role.
6. **One read policy, read only.** "own stewardships readable" is replaced by one permissive SELECT policy for `authenticated`, "stewardships: own, co-steward and staff read", keeping the own-edge and staff arms and adding `private.leads_scope(scope_type, scope_id)`. One permissive policy per command is the house rule since `20261004000000`. There is still no insert, update or delete policy, so every write stays on the service role.

**Rejected.** A deferred constraint trigger counting at commit (the app lands both participants in one statement already, and a BEFORE trigger names the offending row). A unique index on a sorted participant pair (it needs a denormalized column and says nothing about a third row). A CHECK on `conversations.name` or `created_by` (renameConversation still writes a name, and the rule is about people, not labels). A second permissive SELECT policy beside the old one (the multiple_permissive_policies advisor). A leader arm that walks the hierarchy (a hub guide reading its circles' stewards is a wider read than "co-stewards" and nothing asks for it). An inline `exists` over stewardships in the policy (the recursion the original migration avoided).

**Consequences.** A direct message cannot become a group by any path that reaches the table, including the service role, and a conversation that became a room cannot take a member through the old table. A leader reading `stewardships` on the caller session now sees who else stewards their scope; every app read today still goes through the admin client, so nothing in the product changes until a caller-session reader is written. Reversal is in the migration header. The pgTAP file `supabase/tests/conversation_one_to_one_and_co_steward_read.test.sql` (31 assertions) runs under db-tests; the row's probe replays the migration set and fails on `main` at its first arm.

**Rows.** `HYG-139` (closed).
