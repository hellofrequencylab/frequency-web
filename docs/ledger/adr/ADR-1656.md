## ADR-1656: An over-budget build keeps the compiler cache it restored instead of trimming it, so the next build compiles warm (HYG-140)

**Status:** Accepted · 2026-09-29 · backlog `HYG-140` (closed here) · amends the fail-safe in [ADR-1086](DECISIONS.md) (`check:cache-budget` trim) and follows [ADR-1619](DECISIONS.md) (`HYG-136`) · no budget moved · no migration

**Context.** `HYG-140` said the compiler cache grows on every warm build, so the trim fires often and each trim makes the next build compile cold. Re-tested against the production build logs of 2026-09-29 (Vercel, read only) before building. The premise holds:

| Build | Turbopack in `.next/cache` | `Uploading build cache` |
|---|---|---|
| dpl_FPi8nw83 (cold, after a trim) | 1293 MiB | 1.25 GB |
| dpl_EMfoJd8r (first warm) | 1459 MiB | 1.36 GB |
| next four | | 1.25, 1.25, 1.32, 1.38 GB |
| dpl_4LyNMq4r | trimmed | 264.71 MB |
| dpl_5kL7y3kd (cold) … dpl_5eZ7TSnN | | 1.25, 1.29, 1.27, 1.35, 1.31, 1.34, 1.42 GB |
| dpl_JCj4zdsa, dpl_4H4zhCnd | trimmed | 264.71 MB each |
| dpl_66VCEbxU (cold), dpl_D2YZ6S2W | 1346 MiB | 1.25, 1.28 GB |

Three trims in 22 production builds, and with `PACKED_PER_RAW` at 0.55 the headroom above a cold compile is about 180 MiB of Turbopack, which one or two warm builds use up. `node_modules` sat at 959 MiB on every build, so all of the movement is Turbopack.

What grows, found by reproducing it on a small Next 16.3.6 Turbopack app (40 routes, 22 warm builds): `.next/cache/turbopack/<version>/` is one log-structured database. Each warm build writes new `.sst` tables and `.meta` index files for what it recompiled, about 12% of the cold size per build. The engine compacts only when a family's duplication passes its own threshold, about every seven builds, and the floor still ratchets because index files for small families are never merged (46 MiB of `.meta` after 22 builds against 1.7 MiB cold).

Two remedies the row suggested were measured and ruled out. Nothing in that directory is an entry that can be pruned by age: every table is referenced by an index, so deleting one leaves a database pointing at a missing file. And `next internal post-build`, the public full-compaction command (`turbopackDatabaseCompact`), reclaimed 0 bytes on a database 70% over its cold size, because the build already compacts at shutdown with the same rules. The engine's growth cannot be undone from outside it. What can be controlled is whether that growth reaches the upload.

**Decision.**

1. **`prebuild` snapshots the cache the build restored.** `scripts/snapshot-turbopack-cache.mjs` hard-links `.next/cache/turbopack` into `.next/cache/turbopack-restored`. Tables, index and blob files are written once and never modified in place (a snapshot's md5 sums held across three warm builds, one of which compacted and deleted tables), so they are linked: no disk, milliseconds. `CURRENT`, `LOG` and other bookkeeping are copied. Anything unexpected (a symlink, a refused link) abandons the snapshot and exits 0, and with no snapshot the gate trims exactly as before.
2. **Before it trims, the gate tries to HOLD.** When this build's cache is over the trim point, and the restored generation has every version directory the new one has and fits under the trim point by itself, the gate puts the restored generation back and drops this build's. The upload stays under the trim point, and the next build starts warm from one build back instead of cold. Verified on the reproduction: a build started from the held generation compiled in 9.5 s against 79 s cold.
3. **`HOLD_LIMIT = 6` refreshes it.** A held generation is frozen, so every build after it recompiles what changed since. After six holds in a row the gate trims as before and the next build compiles a fresh, compact cache. A build whose own cache fits, or that trims, resets the count, which is carried in `.next/cache/turbopack-held.json`. Six is a first reading: a cold compile cost about a minute on 2026-09-29. Re-tune it from the `Compiled successfully in` line of held builds, never to make a run green.
4. **The snapshot never reaches Vercel.** The gate weighs it apart from `.next/cache` (it is links to the same bytes), never lists or trims it, and removes it before the upload on every path.
5. **Nothing else moves.** Ceiling, reserve, `PACKED_PER_RAW`, the `node_modules` floor and the named trim list are unchanged. The trim still runs for a cold build, a compiler upgrade, a restored cache that is itself over, and at the limit, and it prints why the hold was refused.

**Rejected.** Pruning Turbopack files by age (corrupts the database). `next internal post-build` before the upload (measured no-op). Turning `turbopackFileSystemCacheForBuild` off (every build pays the cold compile the trim charges every few). Dropping browser source maps to shrink the cold cache (about 8% on the reproduction, and Sentry uploads them). Raising the trim point or the reserve.

**Consequences.** The trim becomes the refresh rather than the reaction: in the 2026-09-29 pattern it would fire about once every eight builds instead of every two to five. The line to watch in a build log is `HELD the compiler cache … Held N of 6`. If held builds' compile time climbs toward the cold figure before the limit, lower `HOLD_LIMIT`; if it stays flat, it can rise. A Next upgrade still costs one cold compile, as it always did.

**Rows.** `HYG-140` closed here with a cmd probe that runs the real `prebuild` and `postbuild` files against a fixture cache: an over-budget build keeps the restored generation, the hold is counted, the snapshot is gone, and at `HOLD_LIMIT` the trim runs. It fails on main at its first arm. Still to read after merge: several consecutive production builds printing `HELD` or `✅` with no cold compile between refreshes.
