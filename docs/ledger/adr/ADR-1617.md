## ADR-1617: One tab cannot flood member routes: Link prefetches are capped per tab, the proxy stops re-sending marker cookies on Server Actions, and the presence heartbeat has a floor and a backoff (LIVE-649)

**Status:** Accepted · 2026-09-29 · backlog `LIVE-649` (closed here, filed by `HYG-135`) · numbered 1617 by the orchestrator's assignment · re-tested first per [ADR-1082](DECISIONS.md) from the Vercel runtime logs (read only) and a local Next 16.3.6 build · no migration, no config change

**Context.** Vercel runtime logs, read 2026-09-29. Deployment `dpl_DRQ9xhdp6AjEzHmSpQEz89KGCzoP` (`c4b5aedf`) logged 550,824 lines that day, and all but 308 of them were 200s; every sampled line is a GET. Between 14:00 and 14:10Z it served each of 15 shell routes about 860 times (86 a minute each), 490 to 380 for the rail and account links, and `/feed` 2,193 times. A second tab on `dpl_CvaywacE4VK3Tbpcem96dw381hZ8` (`8d201108`) showed the same shape between 16:00 and 16:10Z: every visible Link about 40 times a minute, and no request for the page itself. Both fast phases stopped between 16:00 and 16:30Z. After that the second tab sat on `/spaces/royaltemple` at exactly 2 requests per Link per 90 s (14 per Link in 17:10 to 17:20Z) and 3 for the page. The same shape runs on the production deployments back to 2026-09-27 (`dpl_8Rb79…`, 505,740 lines).

One request per visible Link per cycle is Next's `pingVisibleLinks` (`next/dist/client/components/links.js`). When the router's tree changes or its prefetch cache is invalidated, it schedules every Link on screen again, and nothing in the router puts a ceiling on it. Two causes were found:

- **The 90 s cadence is ours, and it is proven.** The proxy wrote `fq_acct` on every signed-in response, and `fq_ask` on every response in a prior-consent region, to keep the max-age rolling. Next merges a cookie the proxy sets into a Server Action's cookie store (`server/async-storage/request-store.js`, `mergeMiddlewareCookies`). It then reports that action as "cookies changed" (`server/app-render/action-handler.js`, `addRevalidationHeader`), and the client answers with `invalidateEntirePrefetchCache` plus a page refresh (`server-action-reducer.js`). So the presence heartbeat, a Server Action that changes nothing, re-prefetched every visible Link in every open member tab every 90 s and on every visibility change. We reproduced this on a minimal Next 16.3.6 build with the same proxy rule and heartbeat. Four pings in 16 s made 53 requests with the cookie written and 16 without. Driving the same action once a second made 221 requests in 30 s, about one per Link per second, which is the production shape.
- **The fast cycle's clock was not identified, and this ADR says so.** The sampled lines show no POST and no request for the page. That fits a route-cache invalidation inside the router rather than a refresh. Next's own candidate is the dynamic-rewrite retry in `segment-cache/cache.js`: when a prefetch renders a different tree than it asked for, it invalidates the route cache and pings every Link. Its source says "it can't loop" and carries a "TODO: … bounding retries". Our proxy rewrites `/events/<slug>` and `/spaces/<slug>` for members, and every fast phase carried those Links. A `next start` build with the same rewrites did not loop, so this cause is unconfirmed.

Suspects the row named and the evidence cleared: the heartbeat on its own schedule (90 s, not 1.5 s), `router.refresh` loops (no effect in the shell or feed calls it, and the fast phases carry no page request), and a stale action id (no POST, no 4xx or 5xx).

**Decision.**

1. **A prefetch fuse caps every tab, whatever the router does** (`lib/nav/prefetch-fuse.ts`, installed from `instrumentation-client.ts` so it wraps `fetch` before the first prefetch). It counts only requests that carry `next-router-prefetch`: at most 4 per route and 60 per tab in 60 s, and none while the tab is hidden. Past the budget it answers locally with a 429. The router already treats a prefetch that is not `ok` as a rejected entry and retries it on its own 10 s backoff, and a click on that Link still navigates. Navigations and Server Actions never carry the header, so the fuse never touches them. The cap sits on the one request type the loop was made of, so it holds for any trigger, found or not. Replaying the production loop (25 Links every 1.5 s for a minute) lets at most 60 through. The local build fell from 221 requests to 77, and prefetches from 28 per Link to 4.
2. **The proxy writes a marker cookie only when it is missing or on a full page load** (`lib/nav/marker-cookie.ts`, used for `fq_acct` and `fq_ask`). A Server Action or an RSC request that already carries the value gets no Set-Cookie. That takes away the "cookies changed" answer, and with it the whole-cache invalidation, from every member's Server Actions, not only the heartbeat. The rolling max-age is still refreshed on each document load.
3. **The presence heartbeat has a floor and a backoff** (`components/presence/presence-gate.ts`). Two pings never land less than 60 s apart, and the gate is module state, so neither a remount nor a visibility flap can ping again. A failing ping, such as a stale action id after a deploy, doubles its wait up to 30 minutes instead of failing on schedule.

**Not done, and why.**

- **No `deploymentId` or skew-protection change in `next.config.ts`.** The logs show the old tab's requests were answered by its own deployment for nine hours, so no mismatch ever reached it. A `deploymentId` hard-reload would not have fired. No new build can reach a tab running an old bundle that its old deployment keeps serving. It stops when the tab reloads, or when the platform stops routing to the old deployment. That routing is the project's Skew Protection setting, which the read-only project API did not expose. It is an owner setting and is recorded here, not changed.
- The marketplace discovery stamp is still re-signed on any request to a discovery path, Server Actions included. It is the take-rate contract ([ADR-1419](DECISIONS.md)), so changing when it is written is its own decision.

**Consequences.** An idle member tab no longer re-prefetches its Links on the heartbeat. Whatever loop the router can enter, one visible tab asks for at most one prefetch a second, and a hidden tab for none. The row's last check is a 24-hour runtime-log read after this deploys, showing no client above one request a second on member routes. That read is the orchestrator's, after merge.

**Rows.** LIVE-649 (closed). Tests: `lib/nav/prefetch-fuse.test.ts`, `proxy-markers.test.ts` (the real proxy) and `components/presence/heartbeat.test.tsx`. Each fails against the code before this change.
