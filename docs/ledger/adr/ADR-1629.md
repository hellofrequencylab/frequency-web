## ADR-1629: Web push is asked for only by a "Turn on notifications" tap, an iPhone Safari tab is shown the Home Screen step instead of a button, and a denial is never asked again (LIVE-701)

**Status:** Accepted · 2026-09-29 · backlog `LIVE-701` (closed here) · WM, the mobile-site lane of [ADR-1624](DECISIONS.md) (owner replan: the mobile site is active, native iOS stays parked in `DEF-MOBILE`, so this is web push only) · re-tested first per [ADR-1082](DECISIONS.md) · numbered 1629 by the orchestrator's assignment for this wave · no migration

**Context.** Re-tested on `main` at `3be160428` on 2026-09-29, from the repo only. `PushRegistration` (`components/push/registration.tsx`) mounts on every `app/(main)` page and, when `Notification.permission` read `default`, called `Notification.requestPermission()` from its `useEffect`. A permission request with no user gesture is refused by Safari on iPhone and shown as a quiet, collapsed prompt by Chrome, so the one ask a member most needed to see was the one their phone hid. Separately, Safari on iPhone and iPad exposes web push (`PushManager`) only to a site added to the Home Screen and opened from there (16.4+); in a Safari tab the API is simply absent, so feature detection alone reads "unsupported" and hides the one step that would fix it. The Settings grid said "Push notifications require granting your browser permission on first toggle", but no toggle asked.

**Decision.**

1. **The page-load effect never asks.** It still registers `/sw.js`, re-saves an existing subscription, and subscribes a browser whose permission is already `granted` (which shows no prompt). Any other state waits for a tap.
2. **One asker, called from a click.** `enablePushFromTap` in `components/push/subscribe.ts` is the only code in `app/`, `components/` or `lib/` that calls `requestPermission`. Its first await is the permission request itself, so the request runs inside the member's gesture (Safari drops the gesture across an await). It then registers the worker, waits for `serviceWorker.ready` (Chrome refuses to subscribe before the worker is active), subscribes and saves, tearing the browser subscription down if the save fails (the scan2 L5-20 rule, now shared by both paths through `subscribeAndSave`).
3. **One state read.** `pushAvailability(readPushEnv())` in `components/push/availability.ts` is a pure function over the browser: `ios-install` (iPhone, iPod, or an iPad reporting as a touch Mac, not opened standalone) is decided FIRST, before `unsupported` (no service worker, `PushManager` or `Notification`), then `denied`, `granted`, `askable`. Every push control renders from it.
4. **A denial is terminal.** In the `denied` state no control renders a button, and `enablePushFromTap` returns before asking if permission already reads `denied`. Only the browser's own settings undo it, and the card says so. A dismissed prompt (`default` after the tap) is not a denial and keeps the button.
5. **Where the button lives.** `PushSettingsCard` on Settings > Notifications, always, with a line for every state. `PushNudge`, a one-time card beside a moment that earns it: under a Going RSVP (`RsvpControls`) and on a Circle a member belongs to (the Circle layout). It shows only when a tap (or the Home Screen step) can help, at most once per device (a `localStorage` flag, a per-device convenience and never a record), and "Not now" puts it away. The Settings grid's footer points at the card.

**Rejected.** Asking on the first tap anywhere on the page (a prompt the member did not choose is the same surprise with a gesture attached). Hiding the control on an iPhone tab as "unsupported" (the member never learns the fix). A persistent nudge until answered (pushy, and Settings is the way back). An install card with the browser prompt and manifest screenshots (that is `LIVE-703`, which awaits an owner ruling on whether and where to ask). Anything native (`DEF-MOBILE`, parked).

**Consequences.** ✅ No page load asks for permission; the ask happens inside a tap, where iPhone Safari allows it and Chrome shows the full prompt. ✅ An iPhone member in a Safari tab is told to add Frequency to the Home Screen instead of meeting a button that cannot work. ✅ A member who said no is never asked again. ⚠️ Members who never open Settings, RSVP Going, or open a Circle they belong to are not asked at all; that is the cost of not asking on load. ⚠️ The iPad check reads the user agent and touch points, because iPadOS reports itself as a Mac; a future iPadOS that changes either would read as a desktop browser and fall back to plain feature detection. ⚠️ Installing is still undiscoverable beyond this one line until `LIVE-703` is ruled.

**Rows.** `LIVE-701` (closed here). `LIVE-703` (open, awaits its ruling). `DEF-MOBILE` (parked, untouched).
