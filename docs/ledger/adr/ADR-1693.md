## ADR-1693: Storage files get a second home: a nightly cron copies every object changed since its last run, in every bucket, to Cloudflare R2 under <bucket>/<path>, inert until the owner sets the four R2 variables (HYG-144)

**Status:** Accepted · 2026-09-29 · backlog `HYG-144` (filed by `HYG-138`, the 2026-09-29 replan) · owner rulings 2026-09-29: OWN-084 "Nightly copy elsewhere", backup store "Cloudflare R2" · owner step `OWN-088` · re-tested first per [ADR-1082](DECISIONS.md) · migration `20270345010400` (applied by the orchestrator, not by this change) · renumbered 1693 by the orchestrator from the 1636 this branch drafted, which is taken

**Context.** OWN-082's restore rehearsal showed what Supabase's daily backup brings back: the `storage.objects` rows (526 on 2026-09-29), not the files. "Database backups do not include objects stored via the Storage API." Nothing in the tree copied a file anywhere, so a deleted bucket, a bad bulk delete or a lost project lost every avatar, post image, Loom original and recording for good. Re-tested on `main` at `fb91c7b48`: no backup code, no R2 or S3 client, no dependency that signs S3 requests.

**Decision.**

1. **A Vercel cron, `storage-backup`, at 05:20 UTC**, on the repo's cron contract: `rejectUnauthorizedCron`, `withCronHeartbeat('storage-backup', ...)` with the full `CRON_TIME_BUDGET_MS` as its stated budget, `cronBudget(500)` applied to the listing and its clock checked before each object, `maxDuration = 300`, a `CRON_FRESHNESS` daily entry.
2. **What changed is one RPC over `storage.objects`**, `public.backup_storage_objects_since(p_after_at, p_after_id, p_limit)`: every bucket in one keyset walk on `(coalesce(updated_at, created_at), id)`, strictly after the cursor, oldest first, with a five-minute settle window so a late-committing upload cannot fall behind the cursor. The Storage API cannot answer "changed since" (its list is one folder of one bucket with no date filter), and PostgREST does not expose the `storage` schema. SECURITY INVOKER, revoked from `anon` and `authenticated` by name, granted to `service_role`: a member must never list private paths. No index on `storage.objects` (it belongs to the storage service; 526 rows).
3. **Each object streams from a short-lived signed URL to an R2 PUT** under `<bucket>/<path>`, never held in memory, with `accept-encoding: identity` so the length R2 is told is the length it gets. Signed URLs read private buckets the same way as public ones.
4. **The cursor is one `platform_settings` row, `storage_backup_cursor`, written after every object.** A run killed at the ceiling or stopped by a failed PUT resumes after the last object that landed; the timestamp is kept as the database printed it (microseconds), never round-tripped through a Date. A PUT to the same key replaces it, so a repeat is harmless. An object overwritten in Storage passes the cursor again and replaces its copy. An object deleted between listing and reading is passed over.
5. **Caps per run: 500 objects, 1.5 GiB, the 240 s clock.** The first object is always taken so one file above the byte cap (recordings allow 500 MB) cannot block every night after it. A failed copy answers 500 (the wrapper fail-pings) with the object named.
6. **Inert until configured.** Until `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY` and `R2_BACKUP_BUCKET` are all set (blank counts as unset), a run logs `cron.storage_backup.inert` with the missing names, answers 200 and never creates a database client. They ship blank in `.env.example`.
7. **A minimal SigV4 signer over `node:crypto`, not an SDK.** `aws4fetch` is not a dependency and `@aws-sdk/client-s3` is dozens of packages for one PUT; the signer is pinned to three of AWS's published S3 examples. Server-only, and reachable from the cron route alone, so no layout or shared module carries it (docs/DEPLOY-SAFETY.md).
8. **Unmonitored, for now.** The Healthchecks free tier's 20 checks are all `CRON_MONITORED`. The job is in `CRON_UNMONITORED` with its reason and a note: when a check frees up, the owner creates `storage-backup` and the entry moves to `CRON_MONITORED`. Its cursor makes a missed night cheap: the next run copies what the missed one would have.
9. **Deletes are not mirrored and only the latest version is kept.** A file removed from Storage stays in R2; that is what a backup is for. Pruning is an R2 lifecycle rule if the owner ever wants one.

**Rejected.** A scheduled GitHub workflow (a second place to hold the service-role key, and no heartbeat). Walking every bucket through the Storage list API each night (per-folder recursion with no date filter). `@aws-sdk/client-s3` (weight for one call). Buffering each file (a 500 MB recording in function memory). Mirroring deletes (turns a bad bulk delete into two lost copies). Taking a Healthchecks slot from a monitored job without the owner.

**Consequences.** Once OWN-088 is done, every Storage file has a copy in R2 within a night of its last change, and docs/RUNBOOKS.md §7 says how to get one back (one file, or a bucket after a database restore to a new project). The first nights copy everything that exists, 500 files at a time. The cron count is 32 (LIVE-622's `reconcile-transfers` took 31 on main first). The row's probe reads the schedule, the inert-first route, the four variables, the signed PUT, the per-object cursor, the migration's order and revokes, the grant ledger, the monitor partition and the runbook, and runs the signer against AWS's example; it fails on `main`.

**Owner (OWN-088).** Create the R2 bucket; create an R2 API token with Object Read & Write on that bucket only; set the four variables in Vercel Production; redeploy. Optional: add `storage-backup` to `CRON_HEARTBEAT_SKIP` so the unmonitored job stops pinging a check that does not exist.
