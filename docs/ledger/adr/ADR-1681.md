## ADR-1681: A Journey has one stored order for practices and every other block, and the builder draws, moves and drags by it (LIVE-689)

**Status:** Accepted · 2026-09-30 · backlog `LIVE-689` (closed here) · re-tested first per [ADR-1082](DECISIONS.md) · amends [ADR-252](DECISIONS.md) (the J4b structure editor) · no migration

**Context.** `journey_plan_items.sort_order` already orders every block kind among its siblings, and the member's player reads it that way: `lib/journeys/tree.ts` sorts a parent's children by sort_order and interleaves practices, lessons, checks and modules exactly as stored. Re-tested on `main` at `30975a1b0`, the builder did not. `components/journey/v2/journey-editor.tsx` drew each phase as "the lessons, then a Practices group, then the modules" (the J4b §11 grouping), so a practice stored first was drawn last. The up/down arrows (`moveBlockAction`) swapped with the neighbour in stored order, which was often a row drawn somewhere else, so an arrow could appear to do nothing. At the top level an arrow could trade a loose step with a phase. There was no drag. The row's cited `reorderItems` in `lib/journey-plans.ts` took practice ids only and had no caller. The consequence: an operator could not put a lesson before a practice and see it, and what the builder showed was not what a member read.

**Decision.**

1. **One ordering module, shared by the builder and the actions.** `lib/journeys/block-order.ts` is pure and client-safe. `builderSegments` draws a parent's children in stored order, consecutive steps grouped and each module in its place, the way the tree groups them. `builderLeafOrder` is the builder's reading order and must equal the tree's `lessonOrder`. `laneOf`, `moveWithin`, `moveTo` and `planSiblingOrder` are the reorder math.
2. **Lanes.** Under a phase, every child (practice, lesson, check, module) is one lane. Under a module, every child is a step. At the top level, phases and loose steps are two lanes, because the tree turns loose steps into one opening phase whatever their position. A move or a drag stays in its lane.
3. **A lane keeps its slots.** `planSiblingOrder` puts the lane's existing sort_order values, sorted, onto the new order, so an adjacent swap writes exactly two rows and rows outside the lane keep their place. A tie (two rows on one slot) renumbers the lane from its lowest slot. A list that is not exactly the lane (a missing, extra, foreign or repeated id) is refused and nothing is written.
4. **Two actions, one writer.** `moveBlockAction` (the arrows) and the new `reorderBlocksAction` (a drag saves the whole lane) both write through `writeLaneOrder`: one update per moved row, each scoped to the plan, and when one is refused every row already moved is put back, last first (the scan2 L5-13 rule, generalised from two rows to a lane). A failed put-back is logged as `journeys.move_revert_failed`.
5. **The builder draws the stored order.** Phases, modules and steps render in sort_order with a drag grip on each; the arrows stay as the keyboard path. A drop shows the new order at once from the same math and the server's order replaces it on the refresh. The practices-last group is removed; a practice keeps its Pillar chip, so it still reads as a practice.
6. **Dead code goes.** The practice-ids-only `reorderItems` and the "reordering/interleaving with practices is a follow-up" note leave `lib/journey-plans.ts`.

**Rejected.** A new ordering column or a position table (sort_order already covers every block kind, so a migration would only duplicate it). Renumbering the whole lane 0..n-1 on every move (it writes every row for a one-place move). Keeping the Practices group and reordering only inside it (the member never saw that grouping, so the builder would still disagree with the player). A reorder RPC for atomicity (a migration for a write the put-back already keeps consistent). Cross-parent drag, moving a step into another phase (a separate feature; nothing in the row asks for it).

**Consequences.** An operator can put any block before or after any other in its phase or module, by arrow or drag, and the member reads the same order. The builder's J4b §11 "lessons, then the Pillar practices" reading is gone by design; an author who wants that shape arranges it. The row's probe imports the real `block-order.ts` and `tree.ts` and fails on `main` because the module does not exist; the suite holds the actions' writes and put-back and the builder's rendered order.

**Rows.** `LIVE-689` (closed here).
