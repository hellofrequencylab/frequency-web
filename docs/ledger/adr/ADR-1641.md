## ADR-1641: The in-app scanner may use the camera: /scan is served camera=(self), every other path keeps camera=(), and a scanner reached by a soft navigation re-loads as its own document (LIVE-713)

**Status:** Accepted · 2026-09-29 · backlog `LIVE-713` (closed here; filed by HYG-146 under [ADR-1637](DECISIONS.md)) · fixes the header [ADR-170](DECISIONS.md) set against the scanner [ADR-235](DECISIONS.md) shipped · re-tested first per [ADR-1082](DECISIONS.md) · numbered 1641 by the orchestrator's assignment for this wave

**Context.** Re-tested on `main` at `bc1913405` on 2026-09-29: `next.config.ts` served one header set on `/:path*`, and it carried `Permissions-Policy: camera=(), microphone=(), geolocation=(self)` under a comment saying the camera is never used. `components/scan/scanner.tsx` (the ADR-235 scanner: door check-in, Ghost Node and partner plaque capture, member connect codes) calls `getUserMedia`, and an empty allowlist refuses that call for the top-level document itself, so in any browser that enforces the header the scanner opened on its denied card. The premise held.

A sweep of `app/`, `components/`, `lib/` and `hooks/` found ONE camera stream (the scanner). The other camera-shaped code is not governed by this policy: `<input capture>` in the composer, the poster capture and the card capture opens the OS picker, and the poster QR decode (`lib/events/qr-scan.ts`) runs BarcodeDetector over a still image. Nothing records audio (the audio modules only play). Geolocation is asked on many routes (circle maps, location search, Chapters near me, the node claim button, live location, the timezone card, the QR studio) and was already `(self)`.

**Decision.**

1. **Per route, one rule per path.** `/scan` is served `camera=(self), microphone=(), geolocation=(self)`: this origin only, so an embedded YouTube, Stripe or Spotify frame still cannot ask. Every other path keeps `camera=(), microphone=(), geolocation=(self)`. The default rule's source EXCLUDES the camera routes with a lookahead (`/:path((?!(?:scan)/?$).*)`) instead of relying on "the last matching header wins". Next's server does let the later rule win, but a path matched by two rules is where a proxy can send two `Permissions-Policy` lines, and the browser would then decide by emit order. `CAMERA_ROUTES` in `next.config.ts` is the list; the rest of the security headers still apply to every path.
2. **A policy belongs to the document, so the scanner makes sure it has the right one.** A `<Link>` into `/scan` (the partner pages link there) is a soft navigation, and the scanner then runs inside the document the member started on, still under `camera=()`. The refusal is the same NotAllowedError as a member's own Block, so it cannot be told apart afterwards. Before it asks, the scanner reads the document's policy (`document.permissionsPolicy`, else `document.featurePolicy`) and, when it refuses the camera and the document was not loaded at this path, re-loads the URL as its own document with `location.replace`, once. `lib/scan/camera-policy.ts` holds both decisions as pure functions. The loop guard is the navigation timing entry: a document already served for `/scan` never re-loads, it asks and shows the denied card. Browsers that expose neither API do not enforce the header's camera directive, so they ask straight away.
3. **Microphone and geolocation do not move.** No shipped flow records audio, so the microphone stays `()` everywhere. Geolocation stays `(self)` site-wide: it is used across many routes, and narrowing it per route would need the same document re-load in every caller for no gain.

**Rejected.** `camera=(self)` site-wide (the row's alternative): one line and no re-load, but it lets any same-origin script on any page ask for the camera, and the owner's brief asked for the narrowest scope the header system allows. Turning the entry links into plain anchors instead of the scanner check (it fixes today's links and silently breaks on the next `<Link>` or `router.push` to `/scan`; the scanner check covers every way in). A later `/scan` rule over the unchanged `/:path*` rule (correct on Next's own server, but it leaves the answer to one platform's merge order).

**Consequences.** Opening `/scan` directly serves `camera=(self)` and the browser prompts for the camera; tapping in from another page costs one full document load of `/scan` in browsers that enforce the header, then the same prompt. A document first loaded at `/scan` keeps `camera=(self)` while the member moves on inside it by soft navigation; that is the same origin and still needs the member's own grant. Verified on Next 16.3.6's server with the real `headers()`: `/scan` and `/scan?hint=partner` answered one line, `camera=(self), microphone=(), geolocation=(self)`; `/`, `/feed` and `/scanner` answered one line, `camera=(), microphone=(), geolocation=(self)`; `/scan/` 308s to `/scan`. `scripts/permissions-policy.test.ts` reads the policy each path gets the way the router does (Next's config loader, its route normaliser, the `routes-manifest` regex), `lib/scan/camera-policy.test.ts` locks the re-load decision, and `test/e2e/scan-camera.spec.ts` drives the row's 390px case with a fake camera (the header, a direct open, and a soft navigation that re-loads and runs the viewfinder; it needs the e2e job's deploy URL and member session). Any new `getUserMedia` route joins `CAMERA_ROUTES` and does the same document check.
