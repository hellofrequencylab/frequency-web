## ADR-1665: The outcomes report shows completion per Journey from the take and finish tables (LIVE-687)

**Status:** Accepted · 2026-09-29 · backlog `LIVE-687` (closed here) · admin Insights, Outcomes tab · no migration

**Context.** The Journeys section of the outcomes report was always empty. The cause was not a query, a missing join or a wrong status value: `getOutcomeReport` read nothing for Journeys at all. When the legacy `quest_outcomes()` RPC was retired with the action-chain engine (ADR-152 Phase B3), the report kept `quests = []` so consumers compiled, and the promised follow-up never landed. The row asked for "qualifying weeks at or above target_weeks, derived from practice_logs". That derivation is retired too: `lib/journeys/progress.ts` replaced it, and a Journey is now finished at 14 distinct in-window practice days plus the Expression Challenge (`lib/quest/completion.ts`), recorded once as a `journey_completions` row by `lib/quest/complete.ts`. Neither `journey_enrollments` nor `journey_completions` has a status column; a finish is the row existing.

**Decision.**

1. **A take is a `journey_enrollments` row; a finish is a `journey_completions` row.** The report reads the canonical record, not the old weeks bar, because the weeks bar is not what any member is held to.
2. **Members, not rows.** A member counts once per Journey however many takes (a solo take and a Run) or finishes (two seasons) they hold. Started includes anyone with a finish, so a member who finished and then left still counts and the rate never passes 100.
3. **The stall step is lessons checked off plus one**, from `journey_lesson_progress`, averaged over the takers who have not finished; null when all finished. It fills the existing "Stuck at step" column instead of leaving it at a dash.
4. **Every read pages.** PostgREST caps a response at 1,000 rows; a silent cap would under-count the busiest Journey. A failed page logs `[outcomes] <table>` and the section keeps what landed.
5. **The rollup is pure** (`computeJourneyOutcomes`), and `getOutcomeReport` takes the client as an optional argument so fixture rows can drive the whole report.

**Rejected.** Rebuilding qualifying weeks from `practice_logs` (a retired bar). Using `journey_enrollments.completed_at` as the finish (it is a stamp that trails the completion row and was unwritten until recently). A view or RPC (four keyed reads at beta scale need no migration). Dropping the stall column (the data exists).

**Consequences.** The Insights Outcomes tab lists each Journey members took, with takers, finishers, the rate, and the lesson step the rest are on, and the "Need attention" count now includes low-completion Journeys. The AI engagement read (`lib/analytics/engagement-read.ts`) sees Journeys for the first time. Rows are keyed by plan id, since titles can repeat.

**Rows.** `LIVE-687` closed here. Tests: `lib/analytics/outcomes.test.ts` (fixture rows for all four tables, including a 1,500-take page run).
