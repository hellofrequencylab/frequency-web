## ADR-1680: The events-series follow-ups close: /events ranks a series by its best date under a stated sort, its map draws one pin per series with "and N more dates", and both operator pickers head a series' dates with its title (LIVE-684)

**Status:** Accepted · 2026-09-30 · backlog `LIVE-684` · re-tested first per [ADR-1082](DECISIONS.md) · amends [ADR-897](DECISIONS.md) §4.4 (the `electBy` ruling) · no migration

**Context.** `docs/EVENTS-SERIES-BUILD-PLAN.md` §11.1 named six follow-ups that ADR-897 deferred, and LIVE-684 carried them. Each was re-tested on `main` at `30975a1b0`:

- `SERIES-PD` (a `DISTINCT ON` push-down so a `LIMIT` counts series): nothing in `supabase/migrations` pushes the fold down. It needs a functional index and an RPC or view per surface, which is a migration.
- `SERIES-RANK`: `app/(main)/events/index-data.ts` folded with the default election (earliest date) and then sorted, so under Most going a weekly class ranked on its next date's count, not its best.
- `SERIES-PIN`: `/nearby` already said "and N more dates" (`lib/nearby/map-pins.ts`), but the `/events` map was built row by row from the card list, which carries up to `cardsPerSeries` (default 3) dates of one series. It stacked identical pins on one venue and none said the gathering repeats.
- `SERIES-MAIN`: moot. The rail never shipped as the `event-series-dates` layout module the plan drew; no module list names it. It renders as `SeriesDatesRail` (a heading plus a list of date chips) in the `seriesRail` identity slot of `EventDetailTemplate`, full width, where a saved `/events/*` layout cannot move it.
- `SERIES-PICKER`: `/admin/qr` listed the last 100 events as bare titles, so a daily series was up to 61 options reading the same name with no date. The circle Manage "Add an event" picker named the date but repeated the title on every line.
- `SERIES-EMBED`: closed by what shipped. `backfillEventEmbeddings` reads live occurrences and keys each series on its anchor, so an aged-out anchor still acquires a missing vector through its upcoming children, and `updateEvent` and `writeEventCopy` call `embedEvent`, which reads by id with no date gate. The stale-on-rename gap the plan feared never opened.

**Decision.**

1. **One comparator orders and elects (`SERIES-RANK`).** `collapseSeries` accepts `elect` as a comparator (`SeriesRanking<T>`), beside `'earliest'` and `'latest'`. It re-ranks the earliest-first list with a stable sort, so a tie elects the earliest date, and a comparator that answers `NaN` is read as a tie. `dates`, `dateCount` and `hiddenCount` stay earliest-first. `/events` lifts its sort into `compareEvents` and passes it as `elect` under Nearest, Most going and Best match, then sorts with it. The default soonest-first order still elects `'earliest'`. This is not the second ordering branch §4.4 rejected: there is one comparator.
2. **One pin per series (`SERIES-PIN`).** `onePerSeries(rows, folded)` in `lib/events/series.ts` keeps each series' first row in the sorted list and reads its other dates from the same fold (`dateCount - 1`). `EventMapPin` gains `moreDates`; `components/events/events-map.tsx` adds `moreDatesLine` (the `/nearby` copy) to the popup, labels the link "See the event and its dates", and sets `moreCount` so the spot draws as a bubble, as `/nearby` does.
3. **Group, never fold, for operators (`SERIES-PICKER`).** `groupBySeries(rows)` keeps every row, buckets by series key in first-appearance order, titles a bucket by its anchor (or its first date when the anchor aged out) and lists its dates earliest first. `/admin/qr` reads `parent_event_id` and `recurrence_type`, labels each date by the event's own wall clock under an `<optgroup>` of the series title, and gives a one-off "Title · date". The circle Manage picker does the same with its existing date format.
4. **`SERIES-MAIN` and `SERIES-EMBED` are ruled in the plan, not built**, with the evidence above.
5. **`SERIES-PD` leaves this row.** It needs a migration, which this change does not write. The owner files it as its own row.

**Rejected.** Re-adding `electBy: 'input'` (sort first, keep input order): a second ordering path and the unreachable option §4.4 deleted. Electing the best date under the default order too: soonest-first means "what is next", and a far-off popular date there would be wrong. Folding the operator pickers: a check-in code and an attach both belong to one date, so hiding dates hides the thing being picked. Raising the `/admin/qr` read above 100 rows: that is the limit-starvation `SERIES-PD` owns.

**Consequences.** Under Most going, a series' card is its best-attended date, so the card can show a date later than the series' next one; that is the ranking the member asked for. The map shows fewer pins where a series had several cards. The `/admin/qr` event labels now carry dates. `lib/events/series.ts` keeps zero imports. The row's probe runs `collapseSeries`, `onePerSeries` and `groupBySeries` in-process and reads the four wired call sites; it fails on `main`, where none of the three exports exists.

**Rows.** `LIVE-684`.
