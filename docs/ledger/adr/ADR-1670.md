## ADR-1670: A refused Supabase token warns on a PR that touches no migration, and still fails a migration PR and main (HYG-154)

**Status:** Accepted · 2026-09-30 · backlog `HYG-154` (filed and closed here) · owner ruling · amends the ledger rule of `check:migrations` (the "credentials + a fetch failure is a FAILURE" outcome) · no migration

**Context.** From 01:04Z on 2026-09-30 the Supabase Management API answered HTTP 401 `{"message":"Unauthorized"}` to the CI secret `SUPABASE_ACCESS_TOKEN`, and the required `checks` job went red on every open PR at once (#3079, #3085, #3065, #3081, #3086). None of them adds or changes a migration. The same step passed on #3087 at 00:55Z, and the dashboard shows the token unexpired. The guard behaved as written: a read that failed is not a read that agreed. But a dead CI credential is not a defect any of those PRs could cause or fix, and the owner ruled that this kind of thing must stop jamming the queue.

**Decision.**

1. **One status, one condition.** A 401 or 403 from the Management API (matched on the message `loadLedgerPayload` throws) on a pull request whose diff names no file under `supabase/migrations` returns `refused`: exit 0.
2. **Loud, never a pass.** The run prints that the token was refused and that NOTHING was compared, what the tree did prove, and the owner action (a new token in the `SUPABASE_ACCESS_TOKEN` Actions secret, LIVE-273). In Actions it also raises a `::warning` annotation, so it shows on the PR's checks page.
3. **Every doubt is strict.** `prTouchesMigrations` answers `false` only on a `pull_request` run with a base ref whose two-dot diff of the migrations directory against `origin/<base>` is empty. A push to main, a missing base, a failed git read, or any migration file in the diff keeps the old failure.
4. **Main notices.** Every push to main still fails `check:migrations` on a refused token, so main's own CI is the gate that notices the dead credential.
5. **Nothing else moves.** Any other 4xx, a 5xx after retries, a transport failure, an error payload, a collapsed read and a half-armed pair all fail exactly as before.

**Rejected.** Skipping on any fetch failure (a database that is down would read as fine on a migration PR). Making the whole ledger read advisory (the 2026-08-12 lost-migration incident is why it is armed). Waiting on the owner to renew the secret each time (the queue is jammed until then, which is the problem the ruling names).

**Consequences.** A dead or revoked CI token blocks only PRs that change migrations, which are the PRs whose correctness depends on the ledger, and turns main's CI red until it is renewed. Other PRs merge with a visible warning. The row's probe drives `ledgerCheck` with an injected 401 and fails on main before this change.

**Rows.** `HYG-154` (filed and closed here).
